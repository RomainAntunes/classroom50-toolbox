# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A tray app for [Classroom 50](https://github.com/foundation50/classroom50) students, in the spirit of JetBrains Toolbox. It runs from the macOS menu bar, the Windows notification area and the Linux tray. It:

1. Installs prerequisites: git, GitHub CLI (`gh`), and the `gh student` extension (`foundation50/gh-student`).
2. Discovers and tracks Classroom 50 assignment repos: due dates, submission state, grades.
3. Runs student actions: accept, clone, submit, and open in an editor, terminal or file manager.

The first release is for students only. Keep the domain layer role-agnostic so a teacher mode (`gh teacher`) can be added later without a rewrite.

- Repo: `github.com/RomainAntunes/classroom50-toolbox`. License: GPL-3.0, the same as Classroom 50.
- Status: tray, popover, tool detection and install, persisted settings, in-app sign-in, the merged project list (GitHub discovery, editor and folder scan with git status, Pages manifests), grades, Feedback PR activity, unmerged-branch detection, unaccepted assignments, notifications, the tray badge, and accept, clone and submit from the app are done.

## Stack and decisions (settled, don't re-litigate)

- **Tauri v2.** The Rust core lives in `src-tauri/`, and the UI is **Svelte 5 + TypeScript** (Vite) in `src/`. Performance matters: keep the webview bundle small and do the work in Rust, not JS.
- **Native look per OS through theming, not a cross-platform skin.** macOS gets vibrancy/blur and SF system fonts, Windows 11 gets Mica plus Fluent spacing and controls, and Linux follows GNOME/libadwaita (and respects KDE). Choose the theme from the platform at runtime and follow the system light/dark setting. The main surface is a popover-style window anchored to the tray icon, not a normal app window.
- **Auth reuses gh.** Sign in through gh's device flow with the scopes `gh student login` requests (`admin:org read:org repo workflow`, plus `user:email` for members' emails), then read the token with `gh auth token`. `gh student login` itself refuses to run without a terminal, so the app runs `gh auth login --web` directly. There is no separate OAuth app, and the app never stores its own token copy.
- **Installs go through the OS package manager.** That means Homebrew (macOS), winget (Windows) and apt/dnf/pacman (Linux), followed by `gh extension install foundation50/gh-student`. Upgrades use `gh extension upgrade gh-student`. Elevation (sudo/UAC) must be explicit and user-initiated.
- **Alerts:** native OS notifications (approaching due dates, a new grade, feedback, new assignments, a teammate's push), a tray badge for a teammate's push only, and autostart at login (launch hidden).
- **Release:** a GitHub Actions matrix builds dmg, msi/nsis, AppImage, deb and rpm when a PR merges into `main` with a new version, and attaches them to a draft GitHub Release. The owner publishes the draft by hand. The Tauri updater reads `https://github.com/RomainAntunes/classroom50-toolbox/releases/latest/download/latest.json`. Updater artifacts are signed with the Tauri key (kept in CI secrets). OS code signing (Apple notarization, Authenticode) is on hold until the toolbox has more users or funding; `docs/code-signing.md` has the plan (Developer ID for macOS, SignPath Foundation's free OSS signing for Windows) and `release.yml` the commented-out macOS secrets.
- **i18n:** English only, but every user-facing string goes through the i18n layer from the start.

## Classroom 50 contracts the app depends on

Classroom 50 has no server. All state lives in GitHub, so the app reads GitHub directly. Upstream publishes JSON Schemas in `schemas/` that are meant for GUI clients like this one. Validate against them instead of guessing field names.

- **`.classroom50.yaml`** (schema `repo-config-v1`) sits at the root of every accepted repo. Its required keys are `classroom` and `assignment`, and it may also hold `secret` (the unlisted-classroom key). It is **not** always there: `empty_repo` assignments commit no control files (`no_autograder` ones do get the marker, just no workflow), so a repo also counts when its name matches `<classroom>-<assignment>-<user or group>` (lowercase, longest slug wins, see `classroom50::assignment_for_repo`) for an assignment in its classroom's manifest.
- **`assignments.json`** (schema `assignments-v1`) is the published list of a classroom's assignments. It's public and needs no token: `https://<org>.github.io/classroom50/<classroom>[/<secret>]/assignments.json` (see `classroom50::assignments_url`). It holds due dates, release dates (`--available-from`), submission mode and group settings. A due date only marks work as **late** and never blocks it. Only the teacher's "Close submission" makes a repo read-only, so don't show a deadline as "locked".
- **Submissions:** depending on the assignment's mode, either every push to the default branch counts or only `submit/<UTC-timestamp>-<short-sha>` tags do (pushed by `gh student submit`). A teacher-named milestone tag pattern may also grade.
- **Grades:** each graded submission produces a non-draft **GitHub Release** tagged `submit/*` on the student repo, with a `result.json` asset (schema `result-v1`: `score`, `max-score`, `tests[{test-name, passed, score, max-score}]`, `datetime`, ...). GraphQL's `releaseAssets { url }` is a pre-signed download link, so it is fetched without a token, once per new tag. The app keeps each test's name, pass and points (`status::GradeTest`) and lists the failed ones in a row's details, plus a score history (`RemoteRepo.history`, `status::GradeSummary`) of every graded release among the last 10, each `result.json` downloaded once per tag; why a test failed is only in the release body (the runner strips `detail` and captured output from `result.json`).
- **Feedback PR:** opened at accept when the assignment enables it, titled `Feedback`, from the default branch into a `feedback` branch (which never counts as unmerged work). Teacher activity = its comments and reviews not written by the student.
- **Classroom teams:** each classroom has a secret student team `classroom50-<classroom>` whose description is a `classroom-team-v1` JSON record (`name`, `term`, `active`, `secret`, `pages_base_url`). It exists so a student can enumerate their classrooms without access to the private config repo. Staff teams are `classroom50-<classroom>-{teacher,hta,ta}`.
- **Web app:** `https://classroom50.org` (upstream `web/`). A student's page for an assignment is `/<org>/<classroom>/assignments/<assignment>/submission` (see `classroom50::submission_url`), and accepting is `/<org>/<classroom>/assignments/<assignment>/accept[?k=<secret>]` (`classroom50::accept_url`).
- **Group assignments** are GitHub Teams named `classroom50-group-<hash>-<n>`, owning `<classroom>-<assignment>-group-<n>`.
- Student CLI surface: `gh student accept <org> <classroom> <assignment> [--key] [--new-team [--team-name]]`, `submit` (no flags: it reads the key from `.classroom50.yaml`), `invite`, `team list|add`, `whoami`. Shell out to these for mutations instead of reimplementing accept or submit logic, which has many steps and changes upstream. Reading over the GitHub REST API is fine.
- Upstream reference: the wiki at `github.com/foundation50/classroom50/wiki`, especially `gh-student`, `How-Classroom-50-Works`, `Glossary` and `Autograding-Basics`.

## Project discovery (three sources, merged and de-duplicated by `owner/repo`)

1. **GitHub API:** the user's classrooms come from their classroom teams, plus any `.classroom50.yaml` seen. Their repos are those holding the marker file or named after one of the classroom's assignments.
2. **Local scan:** user-chosen folders (4 levels deep) and, unless the `scanEditorProjects` setting is off, the folders editors opened recently (JetBrains IDEs, VS Code and its forks, Zed, Sublime Text, Eclipse, NetBeans, Visual Studio), their parent folders and the default project folders (`~/IdeaProjects`, `~/eclipse-workspace`, `~/Developer`, ...) (`editors.rs`). A clone counts when it holds `.classroom50.yaml` or its GitHub origin matches an assignment repo. This gives local state (uncommitted changes, commits not yet submitted). The home dir itself is never walked: on macOS touching `~/Documents`, `~/Desktop` or `~/Downloads` raises a permission prompt. When a repo is cloned twice, the clone whose `.git/index` changed last is shown.
3. **Clones made by the app** (accept or clone), registered in `clones.json` (app config dir, so clearing the cache keeps it) when they're created and read as a single repo each scan. A plain `git clone` is picked up by source 2 once the folder is watched.

Remote data (due dates, releases) is cached locally. Refresh it on a timer and on tray open, and respect GitHub rate limits through conditional requests (ETags). The app never runs `git fetch` or anything else that writes to a clone on its own: "new commits on GitHub" is found by checking whether GitHub's head commit exists locally (`git cat-file -e`). The one exception is the Pull button, on a click only (`pull.rs`).

## Commands

```sh
pnpm install
pnpm tauri dev                     # run the app (Vite on :1420 + cargo run)
pnpm tauri build                   # release bundles for the current OS
pnpm lint                          # prettier --check + svelte-check
pnpm format                        # prettier --write
cd src-tauri && cargo fmt && cargo clippy --all-targets -- -D warnings
cd src-tauri && cargo test                       # all Rust tests
cd src-tauri && cargo test parses_github_remotes  # single test (name filter)
```

`cargo build` and `cargo clippy` embed the built frontend through `generate_context!`, so run `pnpm build` once on a fresh checkout before using cargo directly.

The dev build is tray-only (no Dock icon, starts hidden). Open it from the tray icon, or launch the binary a second time: the single-instance plugin shows the popover.

## Layout

- `src-tauri/src/lib.rs` wires the plugins, managed state, tray and popover setup, and the command list.
- `commands.rs` is the IPC surface. Each command has a typed twin in `src/lib/api.ts`, and the two must stay in sync because Rust serializes with camelCase.
- `error.rs` holds the one `Error` enum, which crosses IPC as `{ kind, message }`.
- `process.rs` is the only place that spawns programs. It adds the usual install dirs to PATH, because a Finder-launched app has no `/opt/homebrew/bin`; on Windows it also reads PATH from the registry and the per-user install folders (winget's `%LOCALAPPDATA%\Programs`, Scoop, Chocolatey). The path is rebuilt for each program, so a tool installed while the app runs is found without a restart. It also sets `GH_PROMPT_DISABLED` and hides console windows on Windows.
- `platform/{macos,windows,linux}.rs` implement the same functions (install command, extra PATH dirs, open terminal, editor dirs, how to launch each editor) and are selected with `cfg(target_os)`.
- `tools.rs` detects and installs git, gh and gh-student, updates gh-student (`gh extension upgrade gh-student`; git and gh are left to the package manager), and reads gh's auth. The main page shows a Setup section only while a tool is missing; Settings always has a Tools section with versions, Install and Check again; Update appears only when `gh extension upgrade --dry-run` reports a newer gh-student. Installs and updates run through `process::run_streaming` (lines forwarded as they arrive, a time limit: 15 min for package managers, 5 for gh, `Error::TimedOut`; cancel kills the process group) with `platform::install_env()` (Homebrew: no auto-update, dependents check or cleanup, which made a small install silent for most of its time). Rust keeps one job per tool (`ToolJobs`, `tool_jobs`, `cancel_tool_job`) and sends `tool-jobs` on every change, so a row reopened mid-install still shows it (`src/lib/toolJobs.svelte.ts`): a bar and Cancel, no raw output. The bar fills from download percentages and the package manager's step markers (`platform::INSTALL_STEPS`, never stepping back) and stays indeterminate until one shows up (gh prints nothing). Install asks no confirmation; the click is the go-ahead and the OS prompts for a password itself. A failure shows the command's last lines and the command to run in a terminal; installing returns every tool's status, since gh-student depends on gh.
- `accounts.rs` lists gh's github.com accounts (`gh auth status --json hosts`), switches with `gh auth switch` (gh's global setting, so the terminal follows), signs out with `gh auth logout --user` (confirmed first, since the terminal is signed out too) and serves avatars as `data:` URLs, downloaded from `github.com/<login>.png` (the avatar CDN, not the API) at most weekly into `avatars/` in the app cache dir. The footer shows the active account and a native menu to switch, add one (the add path reuses the device flow) or sign out. When gh takes its token from `GH_TOKEN`/`GITHUB_TOKEN` (`AuthStatus.envToken`, the app started from a shell that exports it) gh can't store, switch or widen a login, so the menu only says so and sign-in reports `Error::TokenFromEnv`.
- `login.rs` runs `gh auth login --web --hostname github.com --scopes ...` with no TTY (stdin null, `GH_PROMPT_DISABLED`), which makes gh non-interactive: no prompt, no "Press Enter", and it never opens a browser. It prints the one-time code (`First copy your one-time code: X`, or `One-time code (X) copied to clipboard` with gh's clipboard setting) and the device URL on stderr; they are parsed (escape codes and `\r` stripped) and emitted as `login-device-code`, and the UI opens the URL (`openUrl`; when that fails, e.g. no `xdg-open`, it spells the URL out). No `--git-protocol`, so a user's ssh choice is kept. A 16 min limit backs up the code's 15 min expiry; cancel kills gh (`process::kill_tree`, `taskkill /T` on Windows). On success Rust syncs the new active account itself. `tools::auth_status` reads `gh api --include user` once: the login, and `X-OAuth-Scopes` checked against gh-student's scopes (`missingScopes`, `admin:org` covering `read:org`). A token that predates the app (gh's defaults lack `admin:org` and `workflow`, and gh-student can't widen it without a terminal) gets a "Grant access" prompt in the footer that runs `gh auth refresh` through the same flow (`grant_scopes`). Offline, the status falls back to gh's local login; a 401 counts as signed out. The browser takes focus and hides the popover, so the UI reports success through a system notification.
- Light, dark or system is the `appearance` setting (Settings > General); Rust applies it to the popover with `window.set_theme` at startup and on change (`popover::apply_appearance`), which also drives the webview's `prefers-color-scheme`.
- `settings.rs` stores `settings.json` in the app config dir, written atomically. A corrupt file is moved to `.bak`. On first run (no file) the login item is registered. `apply_launch_at_login` skips this in debug builds, and `get_settings` reports the OS's real login-item state.
- `classroom50.rs` holds the typed upstream contracts, Pages URLs and web app URLs. `discovery.rs` is the local scanner. `editors.rs` reads the editors' recent-project lists from `platform::editor_config_dirs()` and `editor_data_dirs()` and tags each folder with the editor that opened it: JetBrains `recentProjects.xml`/`recentSolutions.xml`, `file://` URIs in VS Code's `storage.json` and `state.vscdb`, paths under the home dir in Zed's SQLite file (raw bytes, no SQLite dependency), Sublime's `folder_history`, NetBeans' `projectui.properties`, Eclipse's `RECENT_WORKSPACES` and Visual Studio's `ApplicationPrivateSettings.xml`. It only reads them. It also opens a clone in an editor (`platform::editor_launcher`: `open -a <app>` on macOS, the exe, JetBrains Toolbox script, CLI or Flatpak elsewhere). Each project carries the `editor` that last opened it (the folder itself, one inside it, or the nearest folder holding it); others use the `defaultEditor` setting, else the first one installed (`src/lib/editor.svelte.ts`). Opening is in the row's context menu only ("Open in X", "Open with"), and a clone made by the app opens in the default editor.
- `github.rs` is the read-only GitHub layer: GraphQL with typed rate-limit errors, and `HttpCache`, which revalidates GETs with ETags and persists bodies in the app cache dir. The token is read from `gh auth token` per sync and never stored.
- `projects.rs` owns the merged project list. A sync lists every repo the user can see (cheap query), reads the user's classroom teams, re-reads `.classroom50.yaml` and the newest `submit/*` tag only for repos whose `pushedAt` changed (aliased batches of 25; bigger batches time out), runs `git status` in each local clone, fetches each classroom's manifest once and computes `pending`. An assignment of a manifest is listed as not accepted (`unaccepted`) unless a repo of the org names it, by its marker or by the naming rule, slugs compared without regard to case; and only while the account's whole repo list is known: nothing is offered signed out, or while a sync stopped before reading every listed repo (`RemoteCache.incomplete`). After identifying the assignment repos, a sync re-reads just those with the status fragment (`status.rs`: branches compared with `HEAD`, the newest graded release, the head commit's `Autograde` workflow run and `classroom50/autograde` commit status (`Grading`: running, or failed when the runner posted `error` or the run broke before posting), the Feedback PR), then compares each clone with GitHub (`git for-each-ref --no-merged`, `git cat-file -e`). The discovery cache is `repos-v2.json` in the app cache dir. A background tick every 30 s decides what is due (`projects::cadence`, from the nearest deadline of unfinished work): a status check (`Mode::Status`, small batches of 3 repos, at most 4 requests in flight) every 1 min in a deadline's last 3 h, every 2 within a day, every 5 within a week, else every 15 with the full sync hourly instead of every 15 min. A failed full sync doesn't count: the snapshot keeps the last good `synced_at` and `checked_at` (the very first sets `synced_at` anyway, so the list shows), and the full sync is retried at the status-check pace (`due_mode`, `full_attempt`). Waking from sleep (wall clock jumping ahead of the monotonic one) syncs after 5 s. A connect or timeout failure is `Error::Offline`: background syncs stop and the tick only probes `api.github.com:443` over TCP (no HTTP request) until it answers. A status check also runs when the popover opens (at most every minute; a full sync instead, at most every 2 min, while the list offers an assignment that can be accepted now, since only a full sync finds a repo accepted on the web or with the CLI) and right after a push or pull (the watcher sees `.git/refs/remotes` or `FETCH_HEAD` change; then again after 1 and 3 min for the grade, then every minute while an autograde run is still going, for 15 min at most; one round at a time). Background syncs never run while GitHub asks to back off (`retry_after`, kept across restarts) or while under 10% of the GraphQL budget is left; class manifests are re-downloaded at most every 10 min. The last snapshot and stats are saved to `snapshot.json`, so a restart shows everything at once, only rescans the disk and doesn't sync GitHub before it's due. A status check first compares `gh config get user` (local) with the cached login and turns into a full sync after `gh auth switch`; `alerts.json` starts a new baseline for the new account. Only syncs the user started (`SyncProgress.foreground`) show the spinner and bar. The result goes out as `projects-updated`; progress goes out as `sync-progress` (the titlebar bar): one `fraction` per sync that never steps back, from `sync_progress::Tracker`, where each phase (listing, details, manifests, statuses, scan, clones) gets a share sized by its duration in the last sync of the same mode (`SyncStats.phases`) and that run's step counts stand in until the real ones are known. A sync the user started (or any while offline) first emits a preview: the fresh disk scan and `git status` merged with the last GitHub data and cached manifests (no request), so local state shows at once even when GitHub is slow or down; offline, manifests always come from the cache. Concurrent refreshes share the sync in flight, except after a write the app made (accept, adding a teammate: `refresh_after_write`), which waits for it and runs its own. `refresh_local` rescans the folders only and reuses the last GitHub data (no API call). Status checks, previews and `refresh_local` start from every repo of the last discovery (`last_discovery`, the `repos-v2.json` cache), not from the last snapshot's projects, so a repo recognized by name only that one build dropped (no manifest) comes back with the manifest.
- `groups.rs` reads the user's groups on team assignments. The full sync's teams query already lists their `classroom50-group-<hash>-<n>` teams; one aliased query then reads their members (kept in the discovery cache). Emails are not in that query: GraphQL's `email` needs `user:email`/`read:user`, which `gh student login` doesn't grant, and it fails the whole query; each member's public email comes from the REST profile `users/{login}` (no scope needed) through `HttpCache` with the token, at most daily per login. Never add a GraphQL field that needs a scope beyond `admin:org read:org repo workflow`. A project's group is the team whose prefix matches `sha256(classroom \0 assignment)`, as upstream derives it, and the description's `classroom50/group/v1` record (display name) is only trusted when it hashes back to the team name. The row's details list the group and its members; the menu opens the team on GitHub. Read-only: `team add` and `invite` stay in the CLI.
- `alerts.rs` compares each snapshot with `alerts.json` (app cache dir) and emits `notify` notices (deadline reminder at the tightest reached `notifyHoursBefore`, new grade, grading that failed (once per head commit), new Feedback PR comments, newly published assignment, a teammate's push, classmates joining the user's group, a moved deadline, submissions closed) that the layout words through i18n and sends; the first snapshot is a silent baseline. It also keeps the `unseen` ids (a dot in the list, cleared when the popover hides). The tray badge (`tray::set_badge`, a dot drawn into the icon) is for one thing only: a teammate pushed and the popover hasn't been opened since. `src/lib/notices.ts` words and sends the notices; dev builds get a Developer section in Settings that simulates GitHub down or no internet (`simulate.rs`: every GitHub request and the reachability probe ask `simulate::check` first; release builds ignore it), sends a sample of each kind, lights the badge (`preview_badge`) and switches the platform skin (`data-os`, `src/lib/theme/preview.svelte.ts`, kept in `localStorage`) to check every theme on one machine. In `tauri dev` macOS shows them with Terminal's icon (the plugin borrows `com.apple.Terminal` because the binary isn't bundled); bundled builds use the app's.
- `clones.rs` clones with `gh repo clone owner/repo <cloneFolder>/<repo>` (gh's credentials, so private repos need no git setup) and keeps the registry of app-made clones. The clone folder is the `cloneFolder` setting, asked on the first clone (`src/lib/clone.ts`); "Clone to…" in a row's menu picks another and remembers it. An existing target folder is `Error::PathExists`.
- `student.rs` runs the `gh student` writes (accept, submit, and adding a classmate: `team add` on team assignments, `--key` for unlisted classrooms; `invite` otherwise, run in the clone so it checks a group's size limit; the username is checked to be a GitHub login before it reaches gh; `src/lib/teammate.ts` asks for it with the in-popover `askText` prompt, since the dialog plugin has no text input) with a timeout (`process::run_with_timeout`, which then kills gh and the extension it started: the process group on Unix, `taskkill /T` on Windows), from a non-git cwd for accept. It keeps the CLI's own error line (after `gh-student: `) as `Error::Student`, and a team assignment with no group as `Error::NeedsTeam`. After an accept a full sync runs (again 20 s later when the new repo isn't listed yet, and also after a failed or timed-out accept, which may have made the repo). Accept never prompts, so `src/lib/accept.ts` asks first (public repo, group rules), offers to found a group on `needsTeam`, then offers to clone. Upcoming (`availableFrom` ahead) and locked assignments can't be accepted from the row. Submit doesn't commit locally: it snapshots the working tree (tracked files plus untracked ones that aren't ignored) and pushes it as a new commit on top of GitHub's head, which undoes changes made only on GitHub, so `src/lib/submit.ts` warns when GitHub is ahead, lists new files, refuses deletions not staged with `git rm` (submit would fail on them) and repos without a marker. Afterwards the clone is one commit behind, and `refresh_after_push` runs because no local ref moved. `process.rs` sets `GIT_TERMINAL_PROMPT=0` so a push without credentials fails instead of hanging.
- `pull.rs` is the only write to a clone, and only on a click: `git pull --ff-only origin <default branch>` with gh's credentials passed by `-c` (nothing saved). It refuses uncommitted changes to tracked files (`Error::LocalChanges`), another branch checked out (`OtherBranch`) and diverged history (`Diverged`), so it never leaves a merge or conflict behind; `src/lib/pull.ts` words the refusals. The row shows a Pull button only when a fast-forward can work; the menu always offers it.
- `watch.rs` watches what each sync reports (`projects::watch_targets`): watched folders and known clones recursively, the editors' recent-project files and project folders non-recursively (for those folders only a child being created, removed or renamed counts). It runs `refresh_local` 2s after the last write, so a `git clone`, commit, edit or a project opened in an editor shows up without a GitHub request. Reads and `node_modules`/`target`/dot-dirs other than `.git` (judged below the target) are ignored. It is only rebuilt when the targets change.
- `tray.rs`, `popover.rs` and `updater.rs` handle the tray icon and menu, the anchored window (hide on blur, vibrancy or Mica) and self-update. A native dialog steals focus and would hide the popover, so every dialog-plugin call and every native context menu (`Menu.popup()`) in the UI is wrapped in `withDialog()` (`src/lib/api.ts`), which pins the popover while it is open. The webview's own context menu is disabled outside text fields.
- `calendar.rs` writes the due dates as an `.ics` file (Settings > Calendar > Export, through the dialog plugin's `save`): one event per assignment with a due date, accepted or not, minus hidden ones, as a 1-hour block ending at the deadline (a zero-length event is a hairline), titled with the assignment name only; the notes hold the class, where the work stands (not accepted, submitted, grade) and the group with each member's email (their public GitHub email, read from their REST profile, else the newest non-`noreply` address they commit with in the clone, `projects::commit_emails`), worded by the UI's i18n sent at startup (`set_calendar_labels`), an alarm 1 h before the deadline plus one per `notifyHoursBefore`, UIDs from the list ids so a re-import updates events. The exported path becomes `calendarFile`: `calendar::sync` rewrites it after every sync and when hidden items or reminders change, only when an event changed (`DTSTAMP` aside). On macOS the due dates can also live in a real calendar (Settings > Calendar > Calendar app, `nativeCalendar`): `platform/macos/calendar.rs` (EventKit) asks for access only from that click, then `calendar::sync` writes after every sync, skipping events whose fingerprint is unchanged and removing those gone or left in a previously chosen calendar; what was written is `calendar-events.json` in the app config dir. `Info.plist` holds the usage strings and `Entitlements.plist` the calendars entitlement (hardened runtime). Other OSes report `has_native_calendar() == false` and keep the `.ics` file. There is no subscription feed (no server).
- The Settings footer shows the version and the commit it was built from (`__COMMIT__`, injected by `vite.config.js`, `-dirty` when the tree had changes) with links to GitHub.
- Hiding: the `hidden` setting holds project and unaccepted-assignment ids (`src/lib/hidden.ts`, a row's menu). A whole class can be hidden or folded from the "..." on its section header (`hiddenClasses`, `collapsedClasses`, keyed by `filter::classKey`, `owner/classroom` lowercase); a search unfolds every class. Hidden rows are left out of the list unless a search matches them (they then say "Hidden"), and `alerts::process` drops them (and hidden classes) before comparing, so they send no notification; Settings > General shows the count with Show all.
- The first-run guide (`src/routes/welcome`) shows while the `onboarded` setting is false: what the app does, tools, GitHub sign-in (the footer's `LoginStatus`), clone folder and editor. Every step can be skipped, and Settings > About shows it again. Until the first full sync has finished (`snapshot.syncedAt` unset while signed in), the main page shows a centered "Finding your classrooms" screen with its own bar instead of a half-filled list. A settings file from before the guide existed counts as onboarded (`SettingsStore::load`), so upgrades skip it.
- `src/lib/settings.svelte.ts` holds the shared settings state. Rust is the source of truth: write through `saveSettings`, never mutate locally. It also migrates the v0.1.0 `localStorage` folder list.
- `src/lib/theme/theme.css` holds the semantic tokens plus a skin per `data-os`. Components use tokens only.
- Icons: `assets/icon.svg`, `assets/icon-small.svg` (heavier strokes, used at 44px and below) and `assets/tray.svg` are the sources. The popover's header logo is `src/lib/assets/logo.png` (3x PNG: WebKit renders the SVG's drop shadows at 1x, which blurs it). Never edit `src-tauri/icons/` or that PNG by hand; run `scripts/build-icons.sh` (macOS only, needs `rsvg-convert` and ImageMagick).
- `src/lib/i18n` is a flat `en.json` read through `t(key, params)`. New strings go there.
- The updater public key is in `tauri.conf.json`. The private key and its password are in `~/.tauri/classroom50-toolbox.key{,.password}` locally and in the CI secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Losing them strands existing installs on their current version.
- `site/` is the download page at `romainantunes.github.io/classroom50-toolbox`: plain HTML, CSS and JS, deployed by `pages.yml` when `site/` changes (the workflow copies `assets/icon.svg` in). `download.js` reads the latest published release from the GitHub API in the browser and points the button at the visitor's installer, so releases need no redeploy. Drafts are invisible to it.
- Release: run `pnpm bump X.Y.Z` in the PR, which updates `package.json` (read by `tauri.conf.json`) and `Cargo.toml`. On merge, `release.yml` sees that `vX.Y.Z` has no release yet, builds every platform and creates a draft release with `latest.json`, tagging the merge commit. Merges without a bump build nothing. Publishing the draft ships the update. Don't push tags by hand.

## Conventions

- Keep platform-specific code (package managers, tray behavior, autostart, opening editors) in `platform/`, one file per OS exposing the same functions. The UI never branches on OS for behavior, only for theming.
- Every call to `gh` or `git` goes through one Rust process wrapper that captures stderr and exit codes and returns typed errors. Never build shell strings; pass arguments as a vector.
- Rust owns all state and I/O. Svelte only renders and invokes typed Tauri commands, and receives events for progress and refreshes.
- Tauri permissions are allow-listed in `src-tauri/capabilities/default.json`. A plugin API called from JS needs its permission added there.
- Don't use em-dashes in code, comments or UI strings.
- **Dev builds never write to GitHub.** The owner develops against their real classes, so `process::checked_args` refuses `gh student submit|accept|invite|team add` and `git push` under `debug_assertions`. Never weaken or bypass this, and never run those commands by hand while testing. Test the write paths with unit tests or a throwaway repo the owner sets up.
