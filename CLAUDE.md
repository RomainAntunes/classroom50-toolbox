# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A tray app for [Classroom 50](https://github.com/foundation50/classroom50) students, in the spirit of JetBrains Toolbox. It runs from the macOS menu bar, the Windows notification area and the Linux tray. It:

1. Installs prerequisites: git, GitHub CLI (`gh`), and the `gh student` extension (`foundation50/gh-student`).
2. Discovers and tracks Classroom 50 assignment repos: due dates, submission state, grades.
3. Runs student actions: accept, clone, submit, and open in an editor, terminal or file manager.

The app is for students only, by design. Teacher and TA tooling (creating classrooms, grading, closing submissions) stays in the web app and `gh teacher` and is out of this project's scope.

- Repo: `github.com/RomainAntunes/classroom50-toolbox`. License: GPL-3.0, the same as Classroom 50.
- Status: tray, popover, tool detection and install, persisted settings, in-app sign-in, the merged project list (GitHub discovery, editor and folder scan with git status, Pages manifests), grades, Feedback PR activity, unmerged-branch detection, unaccepted assignments, notifications, the tray badge, and accept, clone, submit, commit and commit & push from the app are done.

## Stack and decisions (settled, don't re-litigate)

- **Tauri v2.** The Rust core lives in `src-tauri/`, and the UI is **Svelte 5 + TypeScript** (Vite) in `src/`. Performance matters: keep the webview bundle small and do the work in Rust, not JS. CI holds the bundle to a budget: `scripts/size-budget.mjs` sums `build/`'s JavaScript and CSS, raw and gzipped, and fails above `scripts/size-budget.json` (set about 15% over the bundle of 2026-10-18 before SvelteKit 3 and the module split, which left it about 12% under: JS 920.2 kB raw, 286.8 kB gzip, CSS 30.0 and 9.1 kB; raise a limit only on purpose, saying why), with a table in the run's summary.
- **Native look per OS through theming, not a cross-platform skin.** macOS gets vibrancy/blur and SF system fonts, Windows 11 gets Mica plus Fluent spacing and controls, and Linux follows GNOME/libadwaita (and respects KDE). Choose the theme from the platform at runtime and follow the system light/dark setting. The main surface is a popover-style window anchored to the tray icon, not a normal app window.
- **Auth reuses gh.** Sign in through gh's device flow with the scopes `gh student login` requests (`admin:org read:org repo workflow`, plus `user:email` for members' emails), then read the token with `gh auth token`. `gh student login` itself refuses to run without a terminal, so the app runs `gh auth login --web` directly. There is no separate OAuth app, and the app never stores its own token copy.
- **Installs go through the OS package manager.** That means Homebrew (macOS; git comes from Apple's Command Line Tools), winget (Windows) and apt/dnf/pacman/zypper through `pkexec` (Linux; gh from GitHub's own apt/rpm repository, since the distributions' gh is too old), followed by `gh extension install foundation50/gh-student`. Upgrades use `gh extension upgrade gh-student`. Elevation (sudo/UAC) must be explicit and user-initiated.
- **Alerts:** native OS notifications (approaching due dates, a new grade, feedback, new assignments, a teammate's push), a tray badge for a teammate's push only, and autostart at login (launch hidden).
- **Release:** a GitHub Actions matrix builds dmg (Apple Silicon and Intel), msi/nsis, AppImage, deb and rpm (x64 and Arm64 each) when a PR merges into `main` with a new version, and attaches them to a draft GitHub Release. The owner publishes the draft by hand. A `X.Y.Z-beta.N` version makes a draft pre-release instead (no MSI). The Tauri updater reads `https://github.com/RomainAntunes/classroom50-toolbox/releases/latest/download/latest.json` (stable; GitHub's "latest" never points at a pre-release), or with the `updateChannel` setting on `beta` the `latest.json` of the `beta-channel` release, which `beta-channel.yml` keeps pointing at the newest published release, beta or stable. The app checks every 6 hours, downloads in the background and installs on Restart or Quit. Updater artifacts are signed with the Tauri key (kept in CI secrets). OS code signing (Apple notarization, Authenticode) is on hold until the toolbox has more users or funding; `docs/code-signing.md` has the plan (Developer ID for macOS, SignPath Foundation's free OSS signing for Windows, with its application checklist and a draft code signing policy) and `release.yml` the commented-out macOS secrets and `sign-windows` job: SignPath signs the installers after the build (its origin verification needs them as a workflow artifact, so `signCommand` can't reach it), and since Authenticode changes their bytes the job signs them again with the updater key (`tauri signer sign --app-version`) and rewrites `latest.json`'s signatures, after `updater-urls`.
- **i18n:** English, French, Spanish, German, Italian, Portuguese (Brazil and Portugal), Dutch, Polish, Turkish, Arabic, Hebrew, Simplified Chinese, Japanese and Korean. Address forms: `vous` (fr), `tú` (es), `du` with `ß` (de), `tu` (it, pt-PT), `você` (pt-BR), `je` (nl), `ty` (pl), `siz` (tr), です/ます (ja), 해요체 (ko), 你 (zh-Hans); Arabic and Hebrew never gender the student (verbal nouns, impersonal or infinitive forms) and name the teacher as the teaching staff. The Japanese, Korean, Turkish, Chinese, Arabic and Hebrew catalogs are AI translations not yet reviewed by native speakers; the README's Languages section says so and invites corrections, so update it when one is reviewed. Every user-facing string goes through the i18n layer, and the `language` setting picks a catalog or follows the system.

## Classroom 50 contracts the app depends on

Classroom 50 has no server. All state lives in GitHub, so the app reads GitHub directly. Upstream publishes JSON Schemas in `schemas/` that are meant for GUI clients like this one. Validate against them instead of guessing field names.

- **`.classroom50.yaml`** (schema `repo-config-v1`) sits at the root of every accepted repo. Its required keys are `classroom` and `assignment`, and it may also hold `secret` (the unlisted-classroom key). It is **not** always there: `empty_repo` assignments commit no control files (`no_autograder` ones do get the marker, just no workflow), so a repo also counts when its name matches `<classroom>-<assignment>-<user or group>` (lowercase, longest slug wins, see `classroom50::assignment_for_repo`) for an assignment in its classroom's manifest, or, with neither (a teacher renamed the repo by hand, a deleted marker), when GitHub generated it from an assignment's `template` (`templateRepository`, see `projects::by_template`).
- **Renamed assignments:** `gh teacher assignment rename <org> <classroom> <old> <new>` (one-shot, for a slug whose repo names would pass GitHub's 100 characters) changes the slug and records the old one as the manifest's `renamed_from` (reserved for good), then for each student repo rewrites the marker's `assignment` (`[skip ci]`) and renames the repo to `<classroom>-<new>-<suffix>` (GitHub redirects the old name forever). A repo it failed on keeps the old name and marker until the teacher runs it again. So, like gh-student's markerless submit, a marker or a name may use a slug or its `renamed_from` (`Assignment::answers_to`, `classroom50::assignment_for_slug`; in `assignment_for_repo` the longest prefix still wins and a current slug beats an old one of the same length), and the project carries the current slug. A clone made before the rename keeps an `origin` with the old name: when GitHub lists only the renamed repo, the clone is filed under the new name (`projects::renamed_clone`, same suffix) so the two make one row. Ids change with the name, so after each sync `projects::renamed_ids` lists `(old, new)` for projects (`owner/repo`) and assignments (`org/classroom/slug`): the `hidden` setting follows (saved once, sent as `settings-updated`) and so does `alerts.json` (`alerts::carry_over`: grades, heads, feedback, reminders, unseen...), and a new slug whose `renamed_from` was already known is no new assignment. Students with a marker must `git pull` once before their next `gh student submit`, which would push the old marker back: `student::stale_marker` refuses it with `Error::StaleMarker` while the clone's marker names the old slug and GitHub's doesn't, and `src/lib/submit.ts` offers Pull instead (never submitting right after). Calendar UIDs keep the id from before the rename (`projects::previous_id`), group teams keep the old slug's hash (`groups::find` tries both), and an accept link with the old slug leads to the renamed assignment.
- **`assignments.json`** (schema `assignments-v1`) is the published list of a classroom's assignments. It's public and needs no token: `https://<org>.github.io/classroom50/<classroom>[/<secret>]/assignments.json` (see `classroom50::assignments_url`). It holds due dates, release dates (`--available-from`), submission mode and group settings. A due date only marks work as **late** and never blocks it. Only the teacher's "Close submission" makes a repo read-only, so don't show a deadline as "locked".
- **Submissions:** depending on the assignment's mode, either every push to the default branch counts or only `submit/<UTC-timestamp>-<short-sha>` tags do (pushed by `gh student submit`). A teacher-named milestone tag pattern may also grade.
- **Grades:** each graded submission produces a non-draft **GitHub Release** tagged `submit/*` on the student repo, with a `result.json` asset (schema `result-v1`: `score`, `max-score`, `tests[{test-name, passed, score, max-score}]`, `datetime`, ...). GraphQL's `releaseAssets { url }` is a pre-signed download link, so it is fetched without a token, once per new tag. The app keeps each test's name, pass and points (`status::GradeTest`) and lists the failed ones in a row's details, plus a score history (`RemoteRepo.history`, `status::GradeSummary`) of every graded release among the last 10, each `result.json` downloaded once per tag. Why a test failed is only in the release body (the runner strips `detail` and captured output from `result.json`); upstream's `runner.py` (`render_declarative_body`) writes a `### classroom50 autograde: X/Y` heading, a `| Test | Result | Score |` table, a `<details><summary>Failure details</summary>` section with `**<test-name>**` then a fenced block per failed test (fence longer than any backtick run inside, each captured stream clipped at 2000 chars with `... (truncated)`), an optional `Test output` section for passing `show-output` tests, a `Status:` line and maybe a list of files `allowed_files` removed; a custom autograder writes any Markdown. So when the newest grade has a failed test, a status check reads that one release's body once per tag (`status::release_body`, GraphQL `release(tagName:) { description }`, never in the shared fragment) and `failures::parse` splits it: each failed test's output (`GradeTest.output`, matched by name in order, escape sequences stripped, 6 KB per test and 32 KB per grade, `outputClipped`), and everything else as plain text (`Grade.releaseNotes.notes`, 4 KB; the runner's heading, table, `Status:` line and sections are dropped only when the body has its `### classroom50 autograde:` heading, a custom report keeps its tables and sections, `<details>`/`<summary>` tags aside). `releaseNotes: None` means not read yet, so grades cached before this are read once. A test the runner stopped at its time limit starts with `timed out after <N>s` (`_timeout_outcome`); since upstream's cli 1.58.0 (#1114) what it was fed and flushed before the kill follows (`--- input ---` under `full` only, `--- actual stdout ---` and `--- stderr ---` for `io`, `--- output ---` for `run`/`python`), while older runners, which classes keep in their template repos for a long time, write the line alone. In a runner body (its heading present) that exact first line becomes `GradeTest.timedOutAfter` (seconds; `None` in grades read before) and is dropped from `output`; a custom autograder's text is never read for it. Real bodies from both runners are fixtures in `src-tauri/fixtures/release-bodies/`. In a row's details (`Details.svelte`) a failed test with output or a timeout opens on it: a timed-out one leads with "Stopped after {duration}" (`secondsLabel`, exact seconds) and a hint that output it hadn't flushed is lost, so a prompt may be missing; the output is plain preformatted text (`--font-mono`, no Markdown rendering, no `{@html}`), cut-short output links to the release, and the leftover text opens as "Autograder report".
- **Feedback PR:** opened at accept when the assignment enables it, titled `Feedback`, from the default branch into a `feedback` branch (which never counts as unmerged work). Teacher activity = its comments and reviews not written by the student.
- **Classroom teams:** each classroom has a secret student team `classroom50-<classroom>` whose description is a `classroom-team-v1` JSON record (`name`, `term`, `active`, `secret`, `pages_base_url`). It exists so a student can enumerate their classrooms without access to the private config repo. Staff teams are `classroom50-<classroom>-{teacher,hta,ta}`.
- **Web app:** `https://classroom50.org` (upstream `web/`). A student's page for an assignment is `/<org>/<classroom>/assignments/<assignment>/submission` (see `classroom50::submission_url`), and accepting is `/<org>/<classroom>/assignments/<assignment>/accept[?k=<secret>]` (`classroom50::accept_url`).
- **Group assignments** are GitHub Teams named `classroom50-group-<hash>-<n>`, owning `<classroom>-<assignment>-group-<n>`.
- Student CLI surface: `gh student accept <org> <classroom> <assignment> [--key] [--new-team --team-name]`, `submit [--key]` (it reads the key from `.classroom50.yaml`; without one, since gh-student 1.56.0, it finds the assignment from the repo's name in the org's published `classrooms-index.json` and manifests, longest prefix wins, and an unlisted classroom needs `--key`, which it refuses when it contradicts a marker's own), `invite`, `team list|add`, `whoami`. Shell out to these for mutations instead of reimplementing accept or submit logic, which has many steps and changes upstream. Reading over the GitHub REST API is fine.
- Upstream reference: the wiki at `github.com/foundation50/classroom50/wiki`, especially `gh-student`, `How-Classroom-50-Works`, `Glossary` and `Autograding-Basics`.

## Project discovery (three sources, merged and de-duplicated by `owner/repo`)

1. **GitHub API:** the user's classrooms come from their classroom teams, plus any `.classroom50.yaml` seen. Their repos are those holding the marker file, named after one of the classroom's assignments, or, last, generated from an assignment's template: a repo of the classroom's org (never a user's, never the template itself) whose `templateRepository` (read with the repo list, kept in `repos-v2.json`; null when the template is private to the viewer) is the `template` of exactly one manifest entry among the user's classrooms in that org. Only a repo the user may be working in counts: the list's `isTemplate` and `isArchived` false (`ListedRepo::generated_from`: never a template made from the template or an old term's archived repo) and its `viewerPermission` `WRITE`, `MAINTAIN` or `ADMIN` (`RemoteRepo.canPush`, refreshed from the list at every full sync), or `READ`/`TRIAGE` only when the matched entry is `closed`, since Close submission sets every student repo read-only (`by_template`; a teacher's copy or a classmate's public repo of an open assignment is only read), and never one named after another of the org's known classrooms (`<other>-...`, the longest prefix deciding). Several entries sharing it (a reused assignment, one template in two classes) are told apart by the name (the `<classroom>-` prefix, then the slug in it), else nothing matches; `empty_repo` assignments have no template. A template match only fills a gap: it is dropped when its assignment already has a repo found by marker or name, or a second one found by template (`projects::without_doubtful_templates`), so an assignment never gets two rows, calendar events or reminders. A clone without a marker takes the identity GitHub's repo got. Unaccepted detection follows the same matching.
2. **Local scan:** user-chosen folders (4 levels deep) and, unless the `scanEditorProjects` setting is off, the folders editors opened recently (JetBrains IDEs, VS Code and its forks, Zed, Sublime Text, Eclipse, NetBeans, Visual Studio), their parent folders and the default project folders (`~/IdeaProjects`, `~/eclipse-workspace`, `~/Developer`, ...) (`editors.rs`). A clone counts when it holds `.classroom50.yaml` or its GitHub origin matches an assignment repo. This gives local state (uncommitted changes, commits not yet submitted). The home dir itself is never walked: on macOS touching `~/Documents`, `~/Desktop` or `~/Downloads` raises a permission prompt. When a repo is cloned twice, the clone whose `.git/index` changed last is shown.
3. **Clones made by the app** (accept or clone), registered in `clones.json` (app config dir, so clearing the cache keeps it) when they're created and read as a single repo each scan. A plain `git clone` is picked up by source 2 once the folder is watched.

Remote data (due dates, releases) is cached locally. Refresh it on a timer and on tray open, and respect GitHub rate limits through conditional requests (ETags). The app never runs `git fetch` or anything else that writes to a clone on its own: "new commits on GitHub" is found by checking whether GitHub's head commit exists locally (`git cat-file -e`). The exceptions are Pull, Commit and Commit & push, on a click only (`pull.rs`, `push.rs`).

## Layout

- `src-tauri/src/lib.rs` wires the plugins, managed state, tray and popover setup, and the command list.
- `commands/` is the IPC surface, one file per area (`app`, `accounts`, `tools`, `projects`, `settings`, `calendar`, `editors`, `student` for accept, teammates and submit, `git` for clone, pull, commit and push, `updater`, `deeplink`, `diagnostics`, `developer`), each re-exported whole by `mod.rs` (`pub use area::*`), so `lib.rs` names every command `commands::<name>`, listed once (`ipc_commands!`) for `generate_handler!` and for the `bindings` test. That test writes `src/lib/bindings.ts` with specta (`tauri-specta`, a dev-dependency pinned to its release candidate, so the app never links it): every command with its arguments and result, every type they carry (`#[cfg_attr(test, derive(specta::Type))]` on each, serde attributes honored, `#[serde(default)]` dropped since Rust always writes those fields, integers and the few `f32`s as `number`) and `Events`. It fails when the committed file is stale; `UPDATE_GOLDEN=1 cargo test bindings` rewrites it (prettier skips it). `src/lib/api.ts` is typed from it: `api` is the generated `commands` (each rejects with a `CommandError`), its types keep the UI's names (a type serde reads and writes differently is split in two, and the UI takes the `_Serialize` half), `errorKind` returns an `ErrorKind` and the setting lists (`APPEARANCES`...) must name every variant, so a Rust rename, retype or new variant fails svelte-check wherever the UI relies on it, and argument names can't drift since the generated wrappers build the payload. Since that test links the dialog code, the Windows test binary needs the Common Controls v6 manifest too: `build.rs` passes `src-tauri/windows-app-manifest.xml` (tauri-build's own) to the MSVC linker for every binary, tests included, instead of letting tauri-build embed it in the app's exe only (else `STATUS_ENTRYPOINT_NOT_FOUND`).
- `events.rs` names every event Rust sends with its payload type (`ProjectsUpdated` is `projects-updated` with a `Snapshot`...); Rust emits through `IpcEvent::emit` and the UI listens with `onEvent(NAME, handler)` (`src/lib/api.ts`), the payload typed by `Events`.
- `error.rs` holds the one `Error` enum, which crosses IPC as `{ kind, message, params }` (`CommandError`, its `kind` an `ErrorKind` from `error_kinds!`). `errorMessage` (`src/lib/api.ts`) shows `error.<kind>` from the catalog filled with `params` when `en.json` has it, else Rust's message (tool output, GitHub's or gh-student's own words); `error::tests` checks that English says exactly what `Display` says.
- `process.rs` is the only place that spawns programs. It adds the usual install dirs to PATH, because a Finder-launched app has no `/opt/homebrew/bin`; on Windows it also reads PATH from the registry and the per-user install folders (winget's `%LOCALAPPDATA%\Programs`, Scoop, Chocolatey). The path is rebuilt for each program, so a tool installed while the app runs is found without a restart. A stand-in that would only offer to install the program (`platform::is_stub`: macOS's `/usr/bin/git` without the Command Line Tools, which opens Apple's install dialog on every run) counts as not installed, and git is run by its resolved path. On Windows an app execution alias (`winget.exe`) counts as found. It also sets `GH_PROMPT_DISABLED` and hides console windows on Windows.
- `platform/{macos,windows,linux}.rs` implement the same functions (install plan, extra PATH dirs, open terminal, editor dirs, how to launch each editor) and are selected with `cfg(target_os)`.
- `tools.rs` detects and installs git, gh and gh-student, updates gh-student (`gh extension upgrade gh-student`; git and gh are left to the package manager), and reads gh's auth. gh-student's status reads `gh extension list`, and when that fails (it exits 4 while gh is signed out) the extension's folder in gh's data dir (`manifest.yml`'s tag). `gh extension install` needs no sign-in (gh skips its auth check for it); `upgrade` and its `--dry-run` do, and exit code 4 becomes `Error::NotSignedIn`. A gh older than `tools::MIN_GH` (2.81.0, `gh auth status --json`) is `outdated`: its row shows Update, which runs the install again (every plan upgrades). So is a gh-student older than `tools::MIN_GH_STUDENT` (1.56.0, submit without a marker; a version that can't be read never is), whose Update runs `gh extension upgrade gh-student`, since `gh extension install` refuses an installed extension. The main page shows a Setup section only while a tool is missing or outdated; Settings always has a Tools section with versions, Install and Check again; Update appears only when the tool is outdated or `gh extension upgrade --dry-run` reports a newer gh-student. What an install runs is a `platform::InstallPlan`, built per OS by the pure functions in `platform/install.rs` (unit-tested for every OS on any): macOS runs `xcode-select --install` for git (Apple's dialog; the job then waits up to 45 min for git to appear) and `brew install gh` (no Homebrew: `Error::ManualInstall` with GitHub's `.pkg` page); Windows runs `winget install --id Git.Git|GitHub.cli --exact --source winget` with every agreement accepted and `--disable-interactivity` (no `--silent`: the installer shows its progress and may raise UAC), and winget's "already installed / no applicable update" codes count as success, its cancel code as a cancel, its invalid-arguments code (winget before 1.4) as "update App Installer"; Linux runs the package manager through `pkexec --disable-internal-agent` (126, the prompt dismissed, is a cancel), gh from GitHub's repository (apt: a constant `sh -c` script with the keyring the app downloaded passed as `$1`, refreshing only that source and failing when it can't; dnf and zypper: the `.repo` file written, then `install`/`upgrade` or `install --from gh-cli`), git and Arch's `github-cli` from the distribution; read-only systems (`/run/ostree-booted`, NixOS) and systems without `pkexec` use Homebrew when it is there, else `ManualInstall` with the command for a terminal. `ManualInstall` crosses IPC with `url`, `command` and its `ManualReason` (worded as `setup.manualReason.<code>`), and the row offers to open the page. Installs and updates run through `process::run_streaming` (lines forwarded as they arrive, a time limit: 15 min for package managers, 5 for gh, `Error::TimedOut`; cancel kills the process group on Unix and the process tree with `taskkill /T` on Windows; what runs as root or elevated is left to finish) with the plan's environment (Homebrew: no auto-update, dependents check or cleanup, which made a small install silent for most of its time, but `FORCE_API_AUTO_UPDATE` so the formula data isn't stale forever). Rust keeps one job per tool (`ToolJobs`, `tool_jobs`, `cancel_tool_job`) and sends `tool-jobs` on every change, so a row reopened mid-install still shows it (`src/lib/toolJobs.svelte.ts`): a bar and Cancel, no raw output. The bar fills from download percentages or sizes (`1.0 MB / 9.5 MB`, winget in any display language) and the package manager's step markers (`platform::INSTALL_STEPS`, English only, never stepping back) and stays indeterminate until one shows up (gh prints nothing). Install asks no confirmation; the click is the go-ahead and the OS prompts for a password itself. A failure shows the command's last lines and the plan's `manual` command to run in a terminal; installing returns every tool's status, since gh-student depends on gh.
- `accounts.rs` lists gh's github.com accounts (`gh auth status --json hosts`), switches with `gh auth switch` (gh's global setting, so the terminal follows), signs out with `gh auth logout --user` (confirmed first, since the terminal is signed out too) and serves avatars as `data:` URLs, downloaded from `github.com/<login>.png` (the avatar CDN, not the API) at most weekly into `avatars/` in the app cache dir. The footer shows the active account and a native menu to switch, add one (the add path reuses the device flow) or sign out. When gh takes its token from `GH_TOKEN`/`GITHUB_TOKEN` (`AuthStatus.envToken`, the app started from a shell that exports it) gh can't store, switch or widen a login, so the menu only says so and sign-in reports `Error::TokenFromEnv`.
- `credentials.rs` is Settings > Tools' "Git with your GitHub account" row (`GitLogin.svelte`, shown once git, gh and a sign-in are there): `git_credentials` reads every credential helper git applies to `https://github.com` (`git config --includes --get-regexp`, run from the temp folder so no repo's config counts; an empty value resets the list, as git reads it) and says whether gh's `auth git-credential` is one, naming the others (`osxkeychain`, `manager`, `store`...); `set_up_git_credentials` runs `gh auth setup-git --hostname github.com`, which writes the user's **global** git config (the only write outside the app's own files and a clone's `.git/config`), so it runs from a click after a confirm that names the helpers it replaces for github.com. The app's own Pull and Commit & push never needed it (`pull::GH_CREDENTIALS`); this is for git in a terminal or an editor. There is no undo in the app.
- `login.rs` runs `gh auth login --web --hostname github.com --scopes ...` with no TTY (stdin null, `GH_PROMPT_DISABLED`), which makes gh non-interactive: no prompt, no "Press Enter", and it never opens a browser. Background syncs never run while GitHub asks to back off (`retry_after`, kept across restarts) or while under 10% of the GraphQL budget is left; class manifests are re-downloaded at most every 10 min. The last snapshot and stats are saved to `snapshot.json`, so a restart shows everything at once, only rescans the disk and doesn't sync GitHub before it's due. Only syncs the user started (`SyncProgress.foreground`) show the spinner and bar. Concurrent refreshes share the sync in flight, except after a write the app made (accept, adding a teammate: `refresh_after_write`), which waits for it and runs its own. `refresh_local` rescans the folders only and reuses the last GitHub data (no API call). - `noise.rs` is the built-in list of usual global-gitignore entries applied on top of git's own ignore rules, to **untracked** paths only (a tracked file, say a template's `.vscode/settings.json`, is never filtered): folders at any depth (`.idea`, `.vscode`, `.fleet`, `.zed`, `.vs`, `.history`, `.metadata`, `.nova`, `__MACOSX`, `__pycache__`, `node_modules`), names (`.DS_Store`, `Thumbs.db`, `ehthumbs.db`, `desktop.ini`, `.directory`, `._*`) and suffixes (`.iml`, `.swp`, `.swo`, `~`, `.pyc`). `noise::root` names what makes a path noise (the folder with its `/`, or the file), pure and unit-tested. - `push.rs` is Commit & push, for every-push assignments only (no `submissionMode: tag`, assignment known; tag-mode ones keep Submit): `git add --all` (with untracked noise to leave out, `git --literal-pathspecs add --all --pathspec-from-file` naming exactly the commit's paths, so noise is never staged nor hashed; `PushCheck.skipped` lists it by root, file by file in a folder that also holds a file of the commit, and the prompt says "Left out"), `git commit --message=<msg>` (the `=` form, so the dev guard never reads a message as `push`), then `git push origin refs/heads/<b>:refs/heads/<b>` with pull.rs's `-c` credentials (`process::run_with_timeout`: 2 min commit, 5 min push), so local history matches GitHub, unlike `gh student submit`. With a clean tree and local commits ahead it only pushes. `push_check` refuses before any write: another branch or a detached HEAD (`OtherBranch`), a merge/rebase/cherry-pick/revert in progress (`GitInProgress`), GitHub's head not an ancestor of `HEAD` (`git merge-base --is-ancestor`, covers missing and fetched-but-unmerged: `RemoteAhead`, pull first), nothing to commit or push (`NothingToPush`); it lists changed and new files, files over 50 MB, and refuses files over 100 MB (`FileTooLarge`, nothing committed). No `user.name`/`user.email` is `NoIdentity`: `src/lib/push.ts` first offers the signed-in account (`gh api user`: its name, `<id>+<login>@users.noreply.github.com`) written with `git config --local`, never global. A commit that fails after `git add --all` (a hook, signing, the time limit) puts the index file back byte for byte (`SavedIndex`: git's `index.lock` protocol, skipped when HEAD moved or git holds the lock), so the student's staging is kept and the working tree is never touched. A non-fast-forward push is `PushRejected` (the commit stays local). It always pushes GitHub's default branch (`commands::push_target`), so it needs GitHub's data for the repo: the clone's own branch only when GitHub's repo is known to be empty (no default branch, no head), and with no GitHub data (another account, a sync that hasn't listed the repo yet) push isn't offered (`notOnGitHub`). In dev builds `process::ensure_allowed` refuses the push before the commit, so nothing is written; the test pushes to a local bare repo with the same arguments outside the guard. Commit only (`commit_check`, `commit_only`, `push::commit`) is lighter and works on any clone with changes, whatever the submission mode: it refuses only a merge/rebase in progress, nothing to commit (`NothingToCommit`), files over 100 MB and no identity (same flow); any branch, GitHub ahead or closed submissions are fine, it never pushes, so dev builds allow it, and only `refresh_local` follows. `commit_check` also says whether push applies (`pushBlocked`: `tagMode`, `closed`, `notOnGitHub`, or `push_check`'s refusal kind). `push.ts` asks for the message with `askTextAction` (the in-popover prompt with an optional second button; changed files summarized): from "Commit & push…" the main button is Commit & push and the second Commit only, from "Commit…" (every clone with changes) the other way round; when push is blocked only Commit shows, with one line saying why. With nothing to commit, Commit & push confirms a push of the local commits. The late confirm (marked late, never blocked) only comes when pushing; each refusal is worded. The row never shows a Commit or Commit & push button: it shows where the work stands and the menu offers both. `refresh_after_push` follows a push.

- `watch.rs` watches what each sync reports (`projects::watch_targets`): watched folders and known clones recursively, the editors' recent-project files and project folders non-recursively (for those folders only a child being created, removed or renamed counts). - `updater.rs` is self-update. One state machine (`Machine`, pure and unit-tested: idle, checking, downloading `{downloaded, total}`, ready `{version, notes}`, error; a generation per check, so a reset drops a stale check or download) is sent as `update-state` on every change (progress at most every 100 ms) and read with `update_status`; the layout keeps it in `session.update`. Checks: 20 s after every start, then a 60 s tick checks once 6 h have passed on the wall clock (so a laptop that slept catches up; a tick right after waking, the wall clock jumping past the monotonic one, waits one more), not within an hour of a failure, at once for another version or channel (after that hour too when the last try failed; `due`, `woke`; a check counts as done once its download succeeds, so a failed download is retried after an hour; the last check and failure in `update-check.json`, app cache dir; each check logs the version the feed holds, through a `version_comparator` that keeps the plugin's own rule), and Settings > About's "Check for updates" (`check_update`). Background checks fail quietly (logged); the manual one rejects (`offline` when the request never got an answer, `blockedInDev` in dev builds, `noSelfUpdate` for an install that isn't from a bundle). A newer version downloads at once, in memory (the plugin checks the signature on those bytes, so nothing on disk can be swapped before install; a restart downloads it again), with no check while one downloads or waits. Then `notify` sends `updateReady` and the main page's banner (`UpdateBanner.svelte`, also in Settings > About: version, a determinate bar from bytes, indeterminate without a length) asks Restart now (`install_update`: install, then `app.restart()`; on Windows the plugin starts the passive installer and exits, the installer relaunches) or Later (`defer_update`: the banner stays without the question). It never restarts by itself. Quit from the tray or Settings goes through `updater::quit` (`quit_app`; the JS process plugin's `exit` isn't allowed), which first installs a downloaded update where that needs no prompt (`Bundle::installs_on_quit`: the macOS `.app` swap, NSIS with `restart_after_install(false)`, the AppImage rewrite) so the next launch is the new version; Quit is ignored while Restart now installs, which could otherwise leave an AppImage half written. deb and rpm do self-update (the plugin runs `pkexec dpkg -i` / `rpm -U`, then zenity/kdialog and sudo), and the MSI (installed for all users) asks for administrator rights, so those install only on Restart now, since a prompt after Quit would surprise; the banner says it asks for the password. `Bundle` comes from the bundler's marker (`tauri::utils::platform::bundle_type`); unbundled builds can't update. The `updateChannel` setting (Settings > General, a native menu) picks `endpoint` at runtime (`updater_builder().endpoints`); a change drops what the old channel found and checks again. MSI installs stay on stable (pre-releases ship no MSI, and the NSIS installer over an MSI install would install a second copy; the menu is disabled with a hint); back on stable nothing downgrades (the updater only takes newer versions), as the hint says. Dev builds never check; Settings > Developer > Simulate update (`simulate_update`) runs a fake 4 s download to the ready banner and its notification, and Restart then only logs.

- `tests/e2e` holds the UI flows (Playwright, `playwright.config.ts`; not the WebDriver suite in `e2e/`, which drives the real app): the production build served by `vite preview` on :4419 (built by the config's `webServer` at every run), in WebKit, the engine of WKWebView and WebKitGTK, at the popover's 380x560; specs named `*.dev.spec.ts` run instead on `vite dev` (:4420, started after the build) for what only dev builds have, today the right-to-left preview (`rtl.dev.spec.ts`, `localStorage` `dev.previewRtl`). Rust is faked in the page: `harness/browser.ts`, bundled once per run (`harness/bundle.ts`) and injected with `addInitScript` before the app boots, installs `@tauri-apps/api/mocks` (`mockIPC` with events, `mockWindows`) and answers every `invoke` from a `Scenario` (`fixtures.ts`: `scenario()`, `project()`, `unaccepted()`, `updateStatus()`... typed against `src/lib/api.ts`, at package.json's version with its notes read) or from per-command replies (`ok`, `fail(kind, message, params)` shaped like Rust's `Error` with a kind Rust has, `failPlugin(message)` for a plugin, which rejects with its message, `hold` settled later by `app.release`, `pass` for the fake's own answer after a failure); `defer_update` and `install_update` change the update status and send `update-state` as Rust does, and `export_calendar` sets `calendarFile`. It never reaches a real backend, so nothing can write to GitHub, and the shipped bundle holds none of it (`bundle.spec.ts`). The `app` fixture (`app.ts`) records every call (`calls`, `waitForCall`, `writes` for the commands that write), sends Rust events (`emit`: `tool-jobs`, `login-device-code`, `update-state`, `deep-link`...), holds native dialogs until the test answers them (`dialog`, `answer("ok" | "cancel" | "yes" | "no" | a label | a path)`), keeps every native menu popped up so a test picks an item by its text or id (`rowMenu`, `menu`, `pickMenu`), opens Settings (`openSettings`) and records notifications. After each test it fails on a command the fake doesn't know (add a default in `browser.ts` or a reply in the test) and on uncaught page errors. Scenario files go per area (`list`, `welcome`, `setup`, `tools`, `submit`, `push`, `pull`, `clone`, `teammate`, `accept`, `deeplink`, `auth`, `errors`, `update`, `whatsnew`, `shortcut`, `calendar`); `layout.spec.ts` runs every registered catalog in every skin for raw keys, unfilled placeholders, the catalog's `dir` and anything wider than the popover (`checks.ts`, shared with the right-to-left spec); `samples.ts` is a list with every kind of row, shared with `e2e:shots`. A new UI flow, or a change to one, gets a scenario that checks both what is shown and what was or wasn't invoked (a cancel invokes no write). Headless WebKit doesn't paint `backdrop-filter`, so translucent cards look see-through in screenshots. CI runs it in the `e2e` job of `ci.yml` (Ubuntu, the WebKit browser cached, the report uploaded on failure).
- `site/` is the download page at `romainantunes.github.io/classroom50-toolbox`: plain HTML, CSS and JS, deployed by `pages.yml` when `site/` changes (the workflow copies `assets/icon.svg` in). `download.js` reads the latest published release from the GitHub API in the browser and points the button at the visitor's installer, so releases need no redeploy. Drafts are invisible to it. Its screenshots (also used by the README) and the `og:image` card `social.jpg` live in `site/screenshots/`, made by `pnpm site:shots` (`tests/e2e/showcase.shots.ts`) on the e2e harness: the maintainer's account (`RomainAntunes`, his avatar fetched from GitHub at each run, a letter offline) with made-up classes and classmates. `popover-*.webp` are the popover alone with its shadow on a transparent background (the page draws the rest); `list-<os>-<scheme>.webp` lay it over a drawn desktop (menu bar, taskbar or GNOME top bar, a calm neutral wallpaper) with the material the OS would add. All are WebP from `cwebp`; the prompt's card is made opaque since headless WebKit paints no blur. Rerun it after a visible UI change and commit the images. The page stays neutral (system fonts, greys, no brand gradients) so the color comes from the app; its top bar is drawn as a menu bar with the tray icon and a live clock, and the hero popover hangs right below the icon (`.status` is as wide as the popover).
- Release: the usual way is the Bump workflow (`bump.yml`, Actions > Bump > Run workflow on main, with the version and an optional dry run): it runs `pnpm bump`, then `scripts/changelog-ai.mjs`, which has Claude (`claude-opus-5-5`, structured output, the rules in `scripts/changelog-prompt.md`, the draft, the commits and pull requests since the previous tag and the two newest finished changelogs as context) write the notes in every registered catalog; they are checked before they are written (`validateNotes`: every catalog, the same count and kinds as English, no em-dash, nothing that looks like an internal name; one retry with the problems), a changelog already filled in every catalog is kept, and the run's summary shows the notes. The job then runs `release-inputs`' checks, commits `chore: bump version to X.Y.Z` to main as `github-actions[bot]` (never forced, so a main that moved fails the run) and dispatches `release.yml`, since a push with the workflow's token starts no workflow (`ci.yml` doesn't run on that commit either, its code being the commit before's). `ANTHROPIC_API_KEY` is a secret of the `release` environment, limited to main; main must stay pushable by `github-actions` (a ruleset needs a bypass). The other way, for notes written by hand: run `pnpm bump X.Y.Z` in a PR, which updates `package.json` (read by `tauri.conf.json`), `Cargo.toml` and the app's `Cargo.lock` entry (`withVersion` in `scripts/ci-scope.mjs`, no cargo run) and drafts `src/lib/changelog/X.Y.Z.json`; rewrite and translate the draft in the same PR (see Changelogs), or run `node scripts/changelog-ai.mjs X.Y.Z` with a key. On merge, `release.yml` sees that `vX.Y.Z` has no release yet, creates the draft release tagging the merge commit (once, in the `version` job, so the legs never race to make two; an empty draft a run whose builds all failed left is reused and moved to the new commit, so the next merge builds again, while a published release or a draft with assets means nothing to build) and builds every platform into it with `latest.json` (tauri-action's `releaseId`). The matrix: macOS Apple Silicon and Intel (both on `macos-latest`, `--target`), Linux x64 and Arm64 on `ubuntu-22.04` and `ubuntu-22.04-arm` (native, the same glibc), Windows x64 and Arm64 on `windows-latest` (Arm64 cross-compiled with `--target aarch64-pc-windows-msvc`, as Tauri documents; NSIS and WiX run x64). tauri-action names the feed's entries from the target (`linux-aarch64-deb`, `windows-aarch64-nsis`...), and `updater-urls`, after rewriting the asset links, refuses a `latest.json` that lacks one of the `{os}-{arch}` or `{os}-{arch}-{bundle}` entries the matrix builds (`scripts/updater-platforms.mjs`, tested with vitest; no MSI for a pre-release), since the legs add their entries to one file. Two legs merging it at once can drop one's entries, so a feed refused for a missing platform means re-running that leg's build job, which uploads its files again and runs `updater-urls` after it (that job keeps a link it already rewrote, so it can also be re-run alone). `installer-sizes` then writes each installer's size to the run's summary next to the same installer of the newest published release of a lower version (`scripts/installer-sizes.mjs`, the version stripped from the names to match them), warning, never failing, above +20%. gh-student ships no `windows-arm64` binary, so `gh extension install` fails under an Arm64 `gh` (the app's own arch doesn't matter); an x64 `gh`, emulated, works, so `platform::interpret_failure` turns gh's `gh-student unsupported for windows-arm64` into `ManualInstall` (`ManualReason::WindowsArm`: gh's releases page and the winget commands that swap in the x64 gh, `GH_X64`). The release body is the changelog's English entries under New, Improved and Fixed, then a line about downloading the assets (`scripts/release-notes.mjs`, `releaseBody` in `versions.js`; just that line when the file is missing), and tauri-action copies it into `latest.json`'s `notes`. Merges without a bump build nothing. CI (`ci.yml`) spares a bump PR and its merge: when the change is only the version (`package.json`, `Cargo.toml`, the app's `Cargo.lock` entry) and changelog files, `gate` sets scope `bump` (`scripts/ci-scope.mjs`, against the first parent, tested with vitest) and only `release-inputs` runs (the three versions agree, changelogs formatted, the changelog and scripts tests), since the code is the commit before's, already checked; anything else, or the `run-ci` label, runs everything. Publishing the draft ships the update. A beta is `pnpm bump X.Y.Z-beta.N` (the only pre-release form `bump` and `release.yml` accept): the same matrix, NSIS only on Windows (WiX takes numeric pre-release labels only), a draft marked pre-release. Publishing any release runs `beta-channel.yml`, which copies the newest published release's `latest.json` (`scripts/beta-channel.mjs`, semver order, tested with vitest) to the `beta-channel` release, made on first use as a pre-release never marked latest; run it by hand (workflow_dispatch) to repair the feed. Don't push tags by hand.

## Conventions

- Keep platform-specific code (package managers, tray behavior, autostart, opening editors) in `platform/`, one file per OS exposing the same functions. The UI never branches on OS for behavior, only for theming.
- Every call to `gh` or `git` goes through one Rust process wrapper that captures stderr and exit codes and returns typed errors. Never build shell strings; pass arguments as a vector.
- UI imports from `src/lib` use the `#lib/<path>.js` subpath import (package.json `imports`; `x.ts` and `x.svelte.ts` are `#lib/x.js` and `#lib/x.svelte.js`, a component `#lib/components/X.svelte`). SvelteKit 3 has no `$lib` and no `svelte.config.js`: its options (adapter-static with the `index.html` fallback, `version.pollInterval: 0`) are passed to `sveltekit()` in `vite.config.js`.
- Rust owns all state and I/O. Svelte only renders and invokes typed Tauri commands, and receives events for progress and refreshes.
- Tauri permissions are allow-listed in `src-tauri/capabilities/default.json`. A plugin API called from JS needs its permission added there.
- Supply chain: every action in `.github/workflows` is pinned to a full commit SHA with a `# vX.Y.Z` comment (Dependabot moves both; `dtolnay/rust-toolchain` has no tags, so it is pinned to its `stable` branch and bumped by hand), every workflow sets `permissions: {}` and each job asks for what it needs, a checkout keeps no credentials (`persist-credentials: false`) and a `run:` script reads expressions through `env:`, never `${{ }}` inline. `ci.yml` runs zizmor over the workflows and cargo-deny over the Rust tree: `src-tauri/deny.toml` allows only licenses compatible with shipping GPL-3.0-only and crates.io as the only source, duplicate versions only warn, and each ignored advisory carries why it doesn't apply and when to drop it (its advisories job doesn't block a PR, the other checks do). `.github/dependabot.yml` proposes weekly updates after a 7-day cooldown: minor and patch grouped per ecosystem and folder, majors alone, and every `tauri*` crate with every `@tauri-apps/*` package in one `tauri` PR (a multi-ecosystem group), since a plugin's crate and npm package must share a major.minor. Pinned versions (`rust-ini`; `@tauri-apps/cli` at 2.12.2, since 2.12.3 can't bundle a beta's `.rpm`, until tauri-apps/tauri#16336 ships) are ignored there until the pin goes.
- Don't use em-dashes in code, comments or UI strings.
- **Dev builds never write to GitHub.** The owner develops against their real classes, so `process::checked_args` refuses `gh student submit|accept|invite|team add` and `git push` under `debug_assertions`. Never weaken or bypass this, and never run those commands by hand while testing. Test the write paths with unit tests or a throwaway repo the owner sets up.
