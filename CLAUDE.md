# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A tray app for [Classroom 50](https://github.com/foundation50/classroom50) students, in the spirit of JetBrains Toolbox. It runs from the macOS menu bar, the Windows notification area and the Linux tray. It:

1. Installs prerequisites: git, GitHub CLI (`gh`), and the `gh student` extension (`foundation50/gh-student`).
2. Discovers and tracks Classroom 50 assignment repos: due dates, submission state, grades.
3. Runs student actions: accept, clone, submit, and open in an editor, terminal or file manager.

The first release is for students only. Keep the domain layer role-agnostic so a teacher mode (`gh teacher`) can be added later without a rewrite.

- Repo: `github.com/RomainAntunes/classroom50-toolbox`. License: GPL-3.0, the same as Classroom 50.
- Status: tray, popover, tool detection and install, persisted settings, in-app sign-in, the merged project list (GitHub discovery, editor and folder scan with git status, Pages manifests), grades, Feedback PR activity, unmerged-branch detection, unaccepted assignments, notifications, the tray badge, and accept, clone, submit, commit and commit & push from the app are done.

## Stack and decisions (settled, don't re-litigate)

- **Tauri v2.** The Rust core lives in `src-tauri/`, and the UI is **Svelte 5 + TypeScript** (Vite) in `src/`. Performance matters: keep the webview bundle small and do the work in Rust, not JS.
- **Native look per OS through theming, not a cross-platform skin.** macOS gets vibrancy/blur and SF system fonts, Windows 11 gets Mica plus Fluent spacing and controls, and Linux follows GNOME/libadwaita (and respects KDE). Choose the theme from the platform at runtime and follow the system light/dark setting. The main surface is a popover-style window anchored to the tray icon, not a normal app window.
- **Auth reuses gh.** Sign in through gh's device flow with the scopes `gh student login` requests (`admin:org read:org repo workflow`, plus `user:email` for members' emails), then read the token with `gh auth token`. `gh student login` itself refuses to run without a terminal, so the app runs `gh auth login --web` directly. There is no separate OAuth app, and the app never stores its own token copy.
- **Installs go through the OS package manager.** That means Homebrew (macOS; git comes from Apple's Command Line Tools), winget (Windows) and apt/dnf/pacman/zypper through `pkexec` (Linux; gh from GitHub's own apt/rpm repository, since the distributions' gh is too old), followed by `gh extension install foundation50/gh-student`. Upgrades use `gh extension upgrade gh-student`. Elevation (sudo/UAC) must be explicit and user-initiated.
- **Alerts:** native OS notifications (approaching due dates, a new grade, feedback, new assignments, a teammate's push), a tray badge for a teammate's push only, and autostart at login (launch hidden).
- **Release:** a GitHub Actions matrix builds dmg, msi/nsis, AppImage, deb and rpm when a PR merges into `main` with a new version, and attaches them to a draft GitHub Release. The owner publishes the draft by hand. The Tauri updater reads `https://github.com/RomainAntunes/classroom50-toolbox/releases/latest/download/latest.json`. Updater artifacts are signed with the Tauri key (kept in CI secrets). OS code signing (Apple notarization, Authenticode) is on hold until the toolbox has more users or funding; `docs/code-signing.md` has the plan (Developer ID for macOS, SignPath Foundation's free OSS signing for Windows) and `release.yml` the commented-out macOS secrets.
- **i18n:** English, French, Spanish and German (`vous`, `tú`, `du`; German with `ß`). Every user-facing string goes through the i18n layer, and the `language` setting picks a catalog or follows the system.

## Classroom 50 contracts the app depends on

Classroom 50 has no server. All state lives in GitHub, so the app reads GitHub directly. Upstream publishes JSON Schemas in `schemas/` that are meant for GUI clients like this one. Validate against them instead of guessing field names.

- **`.classroom50.yaml`** (schema `repo-config-v1`) sits at the root of every accepted repo. Its required keys are `classroom` and `assignment`, and it may also hold `secret` (the unlisted-classroom key). It is **not** always there: `empty_repo` assignments commit no control files (`no_autograder` ones do get the marker, just no workflow), so a repo also counts when its name matches `<classroom>-<assignment>-<user or group>` (lowercase, longest slug wins, see `classroom50::assignment_for_repo`) for an assignment in its classroom's manifest.
- **`assignments.json`** (schema `assignments-v1`) is the published list of a classroom's assignments. It's public and needs no token: `https://<org>.github.io/classroom50/<classroom>[/<secret>]/assignments.json` (see `classroom50::assignments_url`). It holds due dates, release dates (`--available-from`), submission mode and group settings. A due date only marks work as **late** and never blocks it. Only the teacher's "Close submission" makes a repo read-only, so don't show a deadline as "locked".
- **Submissions:** depending on the assignment's mode, either every push to the default branch counts or only `submit/<UTC-timestamp>-<short-sha>` tags do (pushed by `gh student submit`). A teacher-named milestone tag pattern may also grade.
- **Grades:** each graded submission produces a non-draft **GitHub Release** tagged `submit/*` on the student repo, with a `result.json` asset (schema `result-v1`: `score`, `max-score`, `tests[{test-name, passed, score, max-score}]`, `datetime`, ...). GraphQL's `releaseAssets { url }` is a pre-signed download link, so it is fetched without a token, once per new tag. The app keeps each test's name, pass and points (`status::GradeTest`) and lists the failed ones in a row's details, plus a score history (`RemoteRepo.history`, `status::GradeSummary`) of every graded release among the last 10, each `result.json` downloaded once per tag. Why a test failed is only in the release body (the runner strips `detail` and captured output from `result.json`); upstream's `runner.py` (`render_declarative_body`) writes a `### classroom50 autograde: X/Y` heading, a `| Test | Result | Score |` table, a `<details><summary>Failure details</summary>` section with `**<test-name>**` then a fenced block per failed test (fence longer than any backtick run inside, each captured stream clipped at 2000 chars with `... (truncated)`), an optional `Test output` section for passing `show-output` tests, a `Status:` line and maybe a list of files `allowed_files` removed; a custom autograder writes any Markdown. So when the newest grade has a failed test, a status check reads that one release's body once per tag (`status::release_body`, GraphQL `release(tagName:) { description }`, never in the shared fragment) and `failures::parse` splits it: each failed test's output (`GradeTest.output`, matched by name in order, escape sequences stripped, 6 KB per test and 32 KB per grade, `outputClipped`), and everything else as plain text (`Grade.releaseNotes.notes`, 4 KB; the runner's heading, table, `Status:` line and sections are dropped only when the body has its `### classroom50 autograde:` heading, a custom report keeps its tables and sections, `<details>`/`<summary>` tags aside). `releaseNotes: None` means not read yet, so grades cached before this are read once. In a row's details (`Details.svelte`) a failed test with output opens on it as plain preformatted text (`--font-mono`, no Markdown rendering, no `{@html}`), cut-short output links to the release, and the leftover text opens as "Autograder report".
- **Feedback PR:** opened at accept when the assignment enables it, titled `Feedback`, from the default branch into a `feedback` branch (which never counts as unmerged work). Teacher activity = its comments and reviews not written by the student.
- **Classroom teams:** each classroom has a secret student team `classroom50-<classroom>` whose description is a `classroom-team-v1` JSON record (`name`, `term`, `active`, `secret`, `pages_base_url`). It exists so a student can enumerate their classrooms without access to the private config repo. Staff teams are `classroom50-<classroom>-{teacher,hta,ta}`.
- **Web app:** `https://classroom50.org` (upstream `web/`). A student's page for an assignment is `/<org>/<classroom>/assignments/<assignment>/submission` (see `classroom50::submission_url`), and accepting is `/<org>/<classroom>/assignments/<assignment>/accept[?k=<secret>]` (`classroom50::accept_url`).
- **Group assignments** are GitHub Teams named `classroom50-group-<hash>-<n>`, owning `<classroom>-<assignment>-group-<n>`.
- Student CLI surface: `gh student accept <org> <classroom> <assignment> [--key] [--new-team --team-name]`, `submit` (no flags: it reads the key from `.classroom50.yaml`), `invite`, `team list|add`, `whoami`. Shell out to these for mutations instead of reimplementing accept or submit logic, which has many steps and changes upstream. Reading over the GitHub REST API is fine.
- Upstream reference: the wiki at `github.com/foundation50/classroom50/wiki`, especially `gh-student`, `How-Classroom-50-Works`, `Glossary` and `Autograding-Basics`.

## Project discovery (three sources, merged and de-duplicated by `owner/repo`)

1. **GitHub API:** the user's classrooms come from their classroom teams, plus any `.classroom50.yaml` seen. Their repos are those holding the marker file or named after one of the classroom's assignments.
2. **Local scan:** user-chosen folders (4 levels deep) and, unless the `scanEditorProjects` setting is off, the folders editors opened recently (JetBrains IDEs, VS Code and its forks, Zed, Sublime Text, Eclipse, NetBeans, Visual Studio), their parent folders and the default project folders (`~/IdeaProjects`, `~/eclipse-workspace`, `~/Developer`, ...) (`editors.rs`). A clone counts when it holds `.classroom50.yaml` or its GitHub origin matches an assignment repo. This gives local state (uncommitted changes, commits not yet submitted). The home dir itself is never walked: on macOS touching `~/Documents`, `~/Desktop` or `~/Downloads` raises a permission prompt. When a repo is cloned twice, the clone whose `.git/index` changed last is shown.
3. **Clones made by the app** (accept or clone), registered in `clones.json` (app config dir, so clearing the cache keeps it) when they're created and read as a single repo each scan. A plain `git clone` is picked up by source 2 once the folder is watched.

Remote data (due dates, releases) is cached locally. Refresh it on a timer and on tray open, and respect GitHub rate limits through conditional requests (ETags). The app never runs `git fetch` or anything else that writes to a clone on its own: "new commits on GitHub" is found by checking whether GitHub's head commit exists locally (`git cat-file -e`). The exceptions are Pull, Commit and Commit & push, on a click only (`pull.rs`, `push.rs`).

## Commands

```sh
pnpm install
pnpm tauri dev                     # run the app (Vite on :1420 + cargo run)
pnpm tauri build                   # release bundles for the current OS
pnpm lint                          # prettier --check + svelte-check

cd src-tauri && cargo fmt && cargo clippy --all-targets -- -D warnings
```

The dev build is tray-only (no Dock icon, starts hidden). Open it from the tray icon, or launch the binary a second time: the single-instance plugin shows the popover.

## Layout

- `src-tauri/src/lib.rs` wires the plugins, managed state, tray and popover setup, and the command list.
- `commands.rs` is the IPC surface. Each command has a typed twin in `src/lib/api.ts`, and the two must stay in sync because Rust serializes with camelCase.
- `error.rs` holds the one `Error` enum, which crosses IPC as `{ kind, message, params }`. `errorMessage` (`src/lib/api.ts`) shows `error.<kind>` from the catalog filled with `params` when `en.json` has it, else Rust's message (tool output, GitHub's or gh-student's own words); `error::tests` checks that English says exactly what `Display` says.
- `process.rs` is the only place that spawns programs. It adds the usual install dirs to PATH, because a Finder-launched app has no `/opt/homebrew/bin`; on Windows it also reads PATH from the registry and the per-user install folders (winget's `%LOCALAPPDATA%\Programs`, Scoop, Chocolatey). The path is rebuilt for each program, so a tool installed while the app runs is found without a restart. A stand-in that would only offer to install the program (`platform::is_stub`: macOS's `/usr/bin/git` without the Command Line Tools, which opens Apple's install dialog on every run) counts as not installed, and git is run by its resolved path. On Windows an app execution alias (`winget.exe`) counts as found. It also sets `GH_PROMPT_DISABLED` and hides console windows on Windows.
- `platform/{macos,windows,linux}.rs` implement the same functions (install plan, extra PATH dirs, open terminal, editor dirs, how to launch each editor) and are selected with `cfg(target_os)`.
- `tools.rs` detects and installs git, gh and gh-student, updates gh-student (`gh extension upgrade gh-student`; git and gh are left to the package manager), and reads gh's auth. gh-student's status reads `gh extension list`, and when that fails (it exits 4 while gh is signed out) the extension's folder in gh's data dir (`manifest.yml`'s tag). `gh extension install` needs no sign-in (gh skips its auth check for it); `upgrade` and its `--dry-run` do, and exit code 4 becomes `Error::NotSignedIn`. A gh older than `tools::MIN_GH` (2.81.0, `gh auth status --json`) is `outdated`: its row shows Update, which runs the install again (every plan upgrades). The main page shows a Setup section only while a tool is missing or outdated; Settings always has a Tools section with versions, Install and Check again; Update appears only when `gh extension upgrade --dry-run` reports a newer gh-student. What an install runs is a `platform::InstallPlan`, built per OS by the pure functions in `platform/install.rs` (unit-tested for every OS on any): macOS runs `xcode-select --install` for git (Apple's dialog; the job then waits up to 45 min for git to appear) and `brew install gh` (no Homebrew: `Error::ManualInstall` with GitHub's `.pkg` page); Windows runs `winget install --id Git.Git|GitHub.cli --exact --source winget` with every agreement accepted and `--disable-interactivity` (no `--silent`: the installer shows its progress and may raise UAC), and winget's "already installed / no applicable update" codes count as success, its cancel code as a cancel, its invalid-arguments code (winget before 1.4) as "update App Installer"; Linux runs the package manager through `pkexec --disable-internal-agent` (126, the prompt dismissed, is a cancel), gh from GitHub's repository (apt: a constant `sh -c` script with the keyring the app downloaded passed as `$1`, refreshing only that source and failing when it can't; dnf and zypper: the `.repo` file written, then `install`/`upgrade` or `install --from gh-cli`), git and Arch's `github-cli` from the distribution; read-only systems (`/run/ostree-booted`, NixOS) and systems without `pkexec` use Homebrew when it is there, else `ManualInstall` with the command for a terminal. `ManualInstall` crosses IPC with `url`, `command` and its `ManualReason` (worded as `setup.manualReason.<code>`), and the row offers to open the page. Installs and updates run through `process::run_streaming` (lines forwarded as they arrive, a time limit: 15 min for package managers, 5 for gh, `Error::TimedOut`; cancel kills the process group on Unix and the process tree with `taskkill /T` on Windows; what runs as root or elevated is left to finish) with the plan's environment (Homebrew: no auto-update, dependents check or cleanup, which made a small install silent for most of its time, but `FORCE_API_AUTO_UPDATE` so the formula data isn't stale forever). Rust keeps one job per tool (`ToolJobs`, `tool_jobs`, `cancel_tool_job`) and sends `tool-jobs` on every change, so a row reopened mid-install still shows it (`src/lib/toolJobs.svelte.ts`): a bar and Cancel, no raw output. The bar fills from download percentages or sizes (`1.0 MB / 9.5 MB`, winget in any display language) and the package manager's step markers (`platform::INSTALL_STEPS`, English only, never stepping back) and stays indeterminate until one shows up (gh prints nothing). Install asks no confirmation; the click is the go-ahead and the OS prompts for a password itself. A failure shows the command's last lines and the plan's `manual` command to run in a terminal; installing returns every tool's status, since gh-student depends on gh.
- `accounts.rs` lists gh's github.com accounts (`gh auth status --json hosts`), switches with `gh auth switch` (gh's global setting, so the terminal follows), signs out with `gh auth logout --user` (confirmed first, since the terminal is signed out too) and serves avatars as `data:` URLs, downloaded from `github.com/<login>.png` (the avatar CDN, not the API) at most weekly into `avatars/` in the app cache dir. The footer shows the active account and a native menu to switch, add one (the add path reuses the device flow) or sign out. When gh takes its token from `GH_TOKEN`/`GITHUB_TOKEN` (`AuthStatus.envToken`, the app started from a shell that exports it) gh can't store, switch or widen a login, so the menu only says so and sign-in reports `Error::TokenFromEnv`.
- `login.rs` runs `gh auth login --web --hostname github.com --scopes ...` with no TTY (stdin null, `GH_PROMPT_DISABLED`), which makes gh non-interactive: no prompt, no "Press Enter", and it never opens a browser. It prints the one-time code (`First copy your one-time code: X`, or `One-time code (X) copied to clipboard` with gh's clipboard setting) and the device URL on stderr; they are parsed (escape codes and `\r` stripped) and emitted as `login-device-code`, and the UI opens the URL (`openUrl`; when that fails, e.g. no `xdg-open`, it spells the URL out). No `--git-protocol`, so a user's ssh choice is kept. A 16 min limit backs up the code's 15 min expiry; cancel kills gh (`process::kill_tree`, `taskkill /T` on Windows). On success Rust syncs the new active account itself. `tools::auth_status` reads `gh api --include user` once: the login, and `X-OAuth-Scopes` checked against gh-student's scopes (`missingScopes`, `admin:org` covering `read:org`). A token that predates the app (gh's defaults lack `admin:org` and `workflow`, and gh-student can't widen it without a terminal) gets a "Grant access" prompt in the footer that runs `gh auth refresh` through the same flow (`grant_scopes`). Offline, the status falls back to gh's local login; a 401 counts as signed out. The browser takes focus and hides the popover, so the UI reports success through a system notification.
- Light, dark or system is the `appearance` setting (Settings > General); Rust applies it to the popover with `window.set_theme` at startup and on change (`popover::apply_appearance`), which also drives the webview's `prefers-color-scheme`.
- The UI language is the `language` setting (Settings > General, a native menu: System plus each catalog named in its own language, its `language.name`). `system` resolves the OS's preferred languages (`system_languages`, the `sys-locale` crate: WKWebView's `navigator.languages` reports the bundle's localizations, not the user's) to a catalog, each tried by full tag then base language (`fr-CH` -> `fr`, `es-419` -> `es`), else English (`resolveLocale`, pure). `Info.plist` declares `CFBundleLocalizations` (en, fr, es, de) so macOS dialogs and predefined menu items follow, and the per-app language in System Settings applies; Rust only stores it (anything that isn't a language tag becomes `system`). The layout applies it live (`setLocale`, `<html lang>`) and sends Rust the words it writes itself: calendar notes (`set_calendar_labels`) and the tray menu (`set_tray_labels`, which rebuilds it; English until the UI has sent them). Adding a language is one import plus one entry in `catalogs` (`src/lib/i18n/index.ts`, in the order the menu lists them: en, fr, es, de), plus its code in `CFBundleLocalizations` if it is new there and a `src-tauri/infoplist/<code>.lproj/InfoPlist.strings` (the calendar permission strings, copied into the bundle's `Resources` by `bundle.macOS.files`); only registered catalogs are offered. Catalogs keep GitHub's own words (dépôt, repositorio, Repository) and the git verbs (commit, push, pull) as students see them in their tools; Submit is Rendre, Entregar, Abgeben.
- `settings.rs` stores `settings.json` in the app config dir, written atomically. A corrupt file is moved to `.bak`. On first run (no file) the login item is registered. `apply_launch_at_login` skips this in debug builds, and `get_settings` reports the OS's real login-item state.
- `classroom50.rs` holds the typed upstream contracts, Pages URLs and web app URLs. `discovery.rs` is the local scanner. `editors.rs` reads the editors' recent-project lists from `platform::editor_config_dirs()` and `editor_data_dirs()` and tags each folder with the editor that opened it: JetBrains `recentProjects.xml`/`recentSolutions.xml`, `file://` URIs in VS Code's `storage.json` and `state.vscdb`, paths under the home dir in Zed's SQLite file (raw bytes, no SQLite dependency), Sublime's `folder_history`, NetBeans' `projectui.properties`, Eclipse's `RECENT_WORKSPACES` and Visual Studio's `ApplicationPrivateSettings.xml`. It only reads them. It also opens a clone in an editor (`platform::editor_launcher`: `open -a <app>` on macOS, the exe, JetBrains Toolbox script, CLI or Flatpak elsewhere). Each project carries the `editor` that last opened it (the folder itself, one inside it, or the nearest folder holding it); others use the `defaultEditor` setting, else the first one installed (`src/lib/editor.svelte.ts`). Opening is in the row's context menu only ("Open in X", "Open with"), and a clone made by the app opens in the default editor.
- `github.rs` is the read-only GitHub layer: GraphQL with typed rate-limit errors, and `HttpCache`, which revalidates GETs with ETags and persists bodies in the app cache dir. The token is read from `gh auth token` per sync and never stored.
- `projects.rs` owns the merged project list. A sync lists every repo the user can see (cheap query), reads the user's classroom teams, re-reads `.classroom50.yaml` and the newest `submit/*` tag only for repos whose `pushedAt` changed (aliased batches of 25; bigger batches time out), runs `git status` in each local clone (`--porcelain=v2 -z`; untracked editor, OS and tool files don't count, see `noise.rs`, and a folder git collapsed into one untracked entry is listed again file by file so one holding only a `.DS_Store` doesn't count; `LocalState` names the first 20 changed paths, `changedPaths`, next to the `changedFiles` count, which the row's details list, 10 then "and N more", and the Uncommitted status's hover hint, `files::changedLines`), fetches each classroom's manifest once and computes `pending`. An assignment of a manifest is listed as not accepted (`unaccepted`) unless a repo of the org names it, by its marker or by the naming rule, slugs compared without regard to case; and only while the account's whole repo list is known: nothing is offered signed out, or while a sync stopped before reading every listed repo (`RemoteCache.incomplete`). After identifying the assignment repos, a sync re-reads just those with the status fragment (`status.rs`: branches compared with `HEAD`, the newest graded release, the head commit's `Autograde` workflow run and `classroom50/autograde` commit status (`Grading`: running, or failed when the runner posted `error` or the run broke before posting), the Feedback PR), then compares each clone with GitHub (`git for-each-ref --no-merged`, `git cat-file -e`). The discovery cache is `repos-v2.json` in the app cache dir. A background tick every 30 s decides what is due (`projects::cadence`, from the nearest deadline of unfinished work): a status check (`Mode::Status`, small batches of 3 repos, at most 4 requests in flight) every 1 min in a deadline's last 3 h, every 2 within a day, every 5 within a week, else every 15 with the full sync hourly instead of every 15 min. A failed full sync doesn't count: the snapshot keeps the last good `synced_at` and `checked_at` (the very first sets `synced_at` anyway, so the list shows), and the full sync is retried at the status-check pace (`due_mode`, `full_attempt`). Waking from sleep (wall clock jumping ahead of the monotonic one) syncs after 5 s. A connect or timeout failure is `Error::Offline`: background syncs stop and the tick only probes `api.github.com:443` over TCP (no HTTP request) until it answers. A status check also runs when the popover opens (at most every minute; a full sync instead, at most every 2 min, while the list offers an assignment that can be accepted now, since only a full sync finds a repo accepted on the web or with the CLI) and right after a push or pull (the watcher sees `.git/refs/remotes` or `FETCH_HEAD` change; then again after 1 and 3 min for the grade, then every minute while an autograde run is still going, for 15 min at most; one round at a time). Background syncs never run while GitHub asks to back off (`retry_after`, kept across restarts) or while under 10% of the GraphQL budget is left; class manifests are re-downloaded at most every 10 min. The last snapshot and stats are saved to `snapshot.json`, so a restart shows everything at once, only rescans the disk and doesn't sync GitHub before it's due. A status check first compares `gh config get user` (local) with the cached login and turns into a full sync after `gh auth switch`; `alerts.json` starts a new baseline for the new account. Only syncs the user started (`SyncProgress.foreground`) show the spinner and bar. The result goes out as `projects-updated`; progress goes out as `sync-progress` (the titlebar bar): one `fraction` per sync that never steps back, from `sync_progress::Tracker`, where each phase (listing, details, manifests, statuses, scan, clones) gets a share sized by its duration in the last sync of the same mode (`SyncStats.phases`) and that run's step counts stand in until the real ones are known. A sync the user started (or any while offline) first emits a preview: the fresh disk scan and `git status` merged with the last GitHub data and cached manifests (no request), so local state shows at once even when GitHub is slow or down; offline, manifests always come from the cache. Concurrent refreshes share the sync in flight, except after a write the app made (accept, adding a teammate: `refresh_after_write`), which waits for it and runs its own. `refresh_local` rescans the folders only and reuses the last GitHub data (no API call). Status checks, previews and `refresh_local` start from every repo of the last discovery (`last_discovery`, the `repos-v2.json` cache), not from the last snapshot's projects, so a repo recognized by name only that one build dropped (no manifest) comes back with the manifest.
- `groups.rs` reads the user's groups on team assignments. The full sync's teams query already lists their `classroom50-group-<hash>-<n>` teams; one aliased query then reads their members with their role (`edges { role node }`, kept in the discovery cache): the maintainers are `Group.founders`, a student-formed group's founder (a teacher-formed group has none), the only one `team add` accepts; `None` in a cache from before roles were read. Emails are not in that query: GraphQL's `email` needs `user:email`/`read:user`, which `gh student login` doesn't grant, and it fails the whole query; each member's public email comes from the REST profile `users/{login}` (no scope needed) through `HttpCache` with the token, at most daily per login. Never add a GraphQL field that needs a scope beyond `admin:org read:org repo workflow`. A project's group is the team whose prefix matches `sha256(classroom \0 assignment)`, as upstream derives it, and the description's `classroom50/group/v1` record (display name) is only trusted when it hashes back to the team name. The row's details list the group and its members; the menu opens the team on GitHub. Read-only: `team add` and `invite` stay in the CLI.
- `alerts.rs` compares each snapshot with `alerts.json` (app cache dir) and emits `notify` notices (deadline reminder at the tightest reached `notifyHoursBefore`, new grade, grading that failed (once per head commit), new Feedback PR comments, newly published assignment, a teammate's push, classmates joining the user's group, a moved deadline, submissions closed) that the layout words through i18n and sends; the first snapshot is a silent baseline. It also keeps the `unseen` ids (a dot in the list, cleared when the popover hides). The tray badge (`tray::set_badge`, a dot drawn into the icon) is for one thing only: a teammate pushed and the popover hasn't been opened since. `src/lib/notices.ts` words and sends the notices; dev builds get a Developer section in Settings that simulates GitHub down or no internet (`simulate.rs`: every GitHub request and the reachability probe ask `simulate::check` first; release builds ignore it), sends a sample of each kind, lights the badge (`preview_badge`) and switches the platform skin (`data-os`, `src/lib/theme/preview.svelte.ts`, kept in `localStorage`) to check every theme on one machine. In `tauri dev` macOS shows them with Terminal's icon (the plugin borrows `com.apple.Terminal` because the binary isn't bundled); bundled builds use the app's.
- `clones.rs` clones with `gh repo clone owner/repo <cloneFolder>/<repo>` (gh's credentials, so private repos need no git setup) and keeps the registry of app-made clones. The clone folder is the `cloneFolder` setting, picked on the first clone (`src/lib/clone.ts`). Every clone asks first, naming the destination (`cloneTarget`, tildified) in a native dialog with three custom buttons (the dialog plugin's `buttons: { yes, no, cancel }`, which resolves to the chosen label on every OS): Clone, Choose another folder… (picked and remembered) and Cancel; the post-accept and deep-link offers word that same dialog with their own question (`CloneQuestion`, "Later" as cancel) instead of asking twice, and with no folder set yet they ask their question, then show the picker. A row's Clone with no folder set yet shows the picker first, then the dialog naming the destination, and remembers the folder only on Clone. "Clone to…" in a row's menu picks another folder directly and remembers it. The row shows the clone as running only once it starts, not while the question is up. An existing target folder is `Error::PathExists`.
- `student.rs` runs the `gh student` writes (accept, submit, and adding a classmate: `team add` on team assignments, `--key` for unlisted classrooms; `invite` otherwise, run in the clone so it checks a group's size limit; each username is checked to be a GitHub login before it reaches gh; `src/lib/teammate.ts` asks for them with the in-popover `askText` prompt, since the dialog plugin has no text input, several at once separated by commas or spaces with `@` stripped (`parseUsernames`), and `add_teammates` runs them one by one, returns one result each and runs `refresh_after_write` once so the details list the new members; the results dialog offers "Add another" until Done. On a team assignment the menu says up front when the user isn't the group's founder (`notFounderReason`: not among `founders`, or the teacher forms the groups) instead of letting gh fail) with a timeout (`process::run_with_timeout`, which then kills gh and the extension it started: the process group on Unix, `taskkill /T` on Windows), from a non-git cwd for accept. It keeps the CLI's own error line (after `gh-student: `) as `Error::Student`, and a team assignment with no group as `Error::NeedsTeam`. After an accept a full sync runs (again 20 s later when the new repo isn't listed yet, and also after a failed or timed-out accept, which may have made the repo). Accept never prompts, so `src/lib/accept.ts` asks first with a short summary (`notes`: the repo it creates, `repoName`, with `group-<n>` on team assignments; private or public and owned by the classroom's org; the Feedback PR when enabled; every push or Submit tags; the due date, late but never refused; group rules; the clone offer that follows), offers to found a group on `needsTeam`, then offers to clone. A group is never founded without a name: `AcceptRequest.new_team` is the name, always passed as `--new-team --team-name=<name>` (the `=` form, so a name is never read as a flag) after `student::valid_team_name` (trimmed, not blank, at most 80 UTF-16 units as upstream's web app allows, no control characters; `gh student` itself only trims it), else `Error::InvalidTeamName`; `accept.ts` asks for it with `askText` (OK disabled while blank, Cancel cancels the accept). After founding a group it says how to add teammates later and offers to add them at once (`addToNewGroup`, the same prompt as "Add to my group…"), before the clone offer. An unaccepted student-formed team assignment without a group also has "Create a group…" in its menu (`canFoundGroup`), which skips the summary: it asks the name first (the prompt also names the repo and whether it is public), accepts with it at once, then offers to add teammates. `add_teammates` then finds the group through `student::FoundedGroups` (the accepted assignment's id) when no sync has listed the new repo yet. Upcoming (`availableFrom` ahead) and locked assignments can't be accepted from the row. Submit doesn't commit locally: it snapshots the working tree (tracked files plus untracked ones that aren't ignored) and pushes it as a new commit on top of GitHub's head, which undoes changes made only on GitHub and would send work never committed, so the app only submits a clean clone: `student::submit` refuses anything uncommitted (`push::work_tree`, editor and OS files aside) with `Error::LocalChanges` before gh runs, the row hides Submit while `changedFiles > 0`, and `src/lib/submit.ts` (from the menu, which keeps Submit to explain) says so, offering Commit… when the `commitActions` setting allows it, else pointing to the editor or a terminal, and never submits right after. It also warns when GitHub is ahead, names the untracked editor files gh-student will send anyway (`SubmitCheck.editorFiles`), and refuses repos without a marker (on every-push assignments, which `empty_repo`/`no_autograder` ones are unless they set `submission_mode: tag`, it offers Commit & push instead). Afterwards the clone is one commit behind, and `refresh_after_push` runs because no local ref moved. `process.rs` sets `GIT_TERMINAL_PROMPT=0` so a push without credentials fails instead of hanging.
- `pull.rs` and `push.rs` are the only writes to a clone, and only on a click. `pull.rs`: `git pull --ff-only origin <default branch>` with gh's credentials passed by `-c` (nothing saved). It refuses uncommitted changes to tracked files (`Error::LocalChanges`), another branch checked out (`OtherBranch`) and diverged history (`Diverged`), so it never leaves a merge or conflict behind; `src/lib/pull.ts` words the refusals. The row shows a Pull button only when a fast-forward can work; the menu always offers it.
- The `commitActions` setting (Settings > General, a native menu) decides which of the following the app offers: `none` (the default: no Commit, no Commit & push, and Submit without a marker only explains), `commit` (Commit only; `commit_check` reports `pushBlocked: disabled`) or `push` (both). `commands::allow_commit` enforces it in `commit_check`, `commit_only`, `push_check` and `commit_push`, so the UI hiding the actions isn't the only guard.
- `noise.rs` is the built-in list of usual global-gitignore entries applied on top of git's own ignore rules, to **untracked** paths only (a tracked file, say a template's `.vscode/settings.json`, is never filtered): folders at any depth (`.idea`, `.vscode`, `.fleet`, `.zed`, `.vs`, `.history`, `.metadata`, `.nova`, `__MACOSX`, `__pycache__`, `node_modules`), names (`.DS_Store`, `Thumbs.db`, `ehthumbs.db`, `desktop.ini`, `.directory`, `._*`) and suffixes (`.iml`, `.swp`, `.swo`, `~`, `.pyc`). `noise::root` names what makes a path noise (the folder with its `/`, or the file), pure and unit-tested. It applies to the projects' changed files (hence `uncommitted`, `conflict`, the Pull button, Commit's enablement) and to what Commit and Commit & push hold.
- `push.rs` is Commit & push, for every-push assignments only (no `submissionMode: tag`, assignment known; tag-mode ones keep Submit): `git add --all` (with untracked noise to leave out, `git --literal-pathspecs add --all --pathspec-from-file` naming exactly the commit's paths, so noise is never staged nor hashed; `PushCheck.skipped` lists it by root, file by file in a folder that also holds a file of the commit, and the prompt says "Left out"), `git commit --message=<msg>` (the `=` form, so the dev guard never reads a message as `push`), then `git push origin refs/heads/<b>:refs/heads/<b>` with pull.rs's `-c` credentials (`process::run_with_timeout`: 2 min commit, 5 min push), so local history matches GitHub, unlike `gh student submit`. With a clean tree and local commits ahead it only pushes. `push_check` refuses before any write: another branch or a detached HEAD (`OtherBranch`), a merge/rebase/cherry-pick/revert in progress (`GitInProgress`), GitHub's head not an ancestor of `HEAD` (`git merge-base --is-ancestor`, covers missing and fetched-but-unmerged: `RemoteAhead`, pull first), nothing to commit or push (`NothingToPush`); it lists changed and new files, files over 50 MB, and refuses files over 100 MB (`FileTooLarge`, nothing committed). No `user.name`/`user.email` is `NoIdentity`: `src/lib/push.ts` first offers the signed-in account (`gh api user`: its name, `<id>+<login>@users.noreply.github.com`) written with `git config --local`, never global. A commit that fails after `git add --all` (a hook, signing, the time limit) puts the index file back byte for byte (`SavedIndex`: git's `index.lock` protocol, skipped when HEAD moved or git holds the lock), so the student's staging is kept and the working tree is never touched. A non-fast-forward push is `PushRejected` (the commit stays local). It always pushes GitHub's default branch (`commands::push_target`), so it needs GitHub's data for the repo: the clone's own branch only when GitHub's repo is known to be empty (no default branch, no head), and with no GitHub data (another account, a sync that hasn't listed the repo yet) push isn't offered (`notOnGitHub`). In dev builds `process::ensure_allowed` refuses the push before the commit, so nothing is written; the test pushes to a local bare repo with the same arguments outside the guard. Commit only (`commit_check`, `commit_only`, `push::commit`) is lighter and works on any clone with changes, whatever the submission mode: it refuses only a merge/rebase in progress, nothing to commit (`NothingToCommit`), files over 100 MB and no identity (same flow); any branch, GitHub ahead or closed submissions are fine, it never pushes, so dev builds allow it, and only `refresh_local` follows. `commit_check` also says whether push applies (`pushBlocked`: `tagMode`, `closed`, `notOnGitHub`, or `push_check`'s refusal kind). `push.ts` asks for the message with `askTextAction` (the in-popover prompt with an optional second button; changed files summarized): from the row button or "Commit & push…" the main button is Commit & push and the second Commit only, from "Commit…" (every clone with changes) the other way round; when push is blocked only Commit shows, with one line saying why. With nothing to commit, Commit & push confirms a push of the local commits. The late confirm (marked late, never blocked) only comes when pushing; each refusal is worded. The row shows Commit & push (instead of Submit on every-push rows) only when it can work: GitHub's data known, on the default branch, changes or commits ahead, nothing incoming; the menu always offers it. `refresh_after_push` follows a push.

Second launches go through the single-instance plugin's `deep-link` feature, which skips its own `popover::show` for link arguments (`is_link_launch`). Registration: bundled builds only (macOS `CFBundleURLTypes`, the NSIS/MSI registry, the deb/rpm `.desktop` `MimeType`), so `tauri dev` gets no links; an AppImage registers itself at every start (`register`, a `.desktop` file in the data dir and `xdg-mime default`), since its path can move. An assignment row's menu has "Copy link" (the accept link, with the classroom key; `src/lib/links.ts`, built to read back with `parse`); a project row with a GitHub repo has a "Copy" submenu: the open link ("App link"), the GitHub page, and the clone URLs (HTTPS `.git`, SSH `git@github.com:`, `gh repo clone owner/repo`; `cloneUrls`) led by gh's `git_protocol` (`tools::git_protocol`, `gh config get git_protocol --host github.com`, local config only, HTTPS when unset; cached in the UI and re-read in the background at each menu). Dev builds test links from Settings > Developer > Open link (`simulate_deep_link`, the same `deeplink::handle`; release builds refuse it).

## Conventions

- Keep platform-specific code (package managers, tray behavior, autostart, opening editors) in `platform/`, one file per OS exposing the same functions. The UI never branches on OS for behavior, only for theming.
- Every call to `gh` or `git` goes through one Rust process wrapper that captures stderr and exit codes and returns typed errors. Never build shell strings; pass arguments as a vector.
- Rust owns all state and I/O. Svelte only renders and invokes typed Tauri commands, and receives events for progress and refreshes.
- Tauri permissions are allow-listed in `src-tauri/capabilities/default.json`. A plugin API called from JS needs its permission added there.
- Don't use em-dashes in code, comments or UI strings.
- **Dev builds never write to GitHub.** The owner develops against their real classes, so `process::checked_args` refuses `gh student submit|accept|invite|team add` and `git push` under `debug_assertions`. Never weaken or bypass this, and never run those commands by hand while testing. Test the write paths with unit tests or a throwaway repo the owner sets up.
